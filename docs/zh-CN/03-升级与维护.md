# 03 · 升级与维护

> [English](../en/03-upgrade-maintenance.md) | [简体中文](03-升级与维护.md)

## 1. 升级

升级涉及**两个层面**，而正常情况下**一步就够** —— 因为镜像升级会按版本自动同步 dsh 本体：

| 层面 | 内容 | 更新方式 |
|---|---|---|
| **镜像层** | `entrypoint`、救援脚本、`/opt/dsh-seed`（构建时锁定的 dsh） | `docker compose pull && docker compose up -d` |
| **dsh 本体** | 挂载卷 `/opt/dsh` 里**实际运行**的 dsh | 上面那一步会**自动**同步（见下）；也可单独 `npm install -g` |

### 镜像升级会按版本自动同步 dsh 本体

容器启动时，entrypoint（`scripts/entrypoint.sh` 第 ① 步）会比较**镜像 seed 的版本**与**卷里 dsh 的版本**：

| 情况 | 动作 |
|---|---|
| 卷里没有 dsh | 复制 seed（首启） |
| **seed 版本 > 卷内版本** | **复制 seed** —— 升级镜像后 dsh 自动跟进 |
| 版本相等 | 不动（不重复复制） |
| 卷内版本更新（你在容器内装过更高版本） | **不动**，尊重你的选择 |

启动日志直接给出三个版本，判断「升没升上去」看这一行即可：

```
[entrypoint] dsh version: seed=0.1.7-rc.2 volume(before)=0.1.7-alpha.2 effective=0.1.7-rc.2
```

所以升级通常只需要：

```bash
docker compose pull && docker compose up -d
docker exec dsh dsh --version                       # 期望：镜像 seed 的版本
docker inspect -f '{{.State.Health.Status}}' dsh    # 期望：healthy
docker logs dsh 2>&1 | grep 'dsh version'           # 三个版本一目了然
docker logs dsh 2>&1 | grep -i 'expose-internals'   # 期望：无输出
```

### 单独升级 / 降级 dsh 本体

镜像 seed 不变，或你想装一个**与镜像不同**的版本时，用容器内 npm：

```bash
docker exec dsh npm install -g @deepseek-ai/dsh@<版本>
docker restart dsh
```

> ⚠️ **升级会被保留，降级会被撤销**：装一个比 seed **更高**的版本，下次启动时 `seed < 卷` → 不动，
> 你的版本保留；装一个比 seed **更低**的版本，下次启动会被 seed 覆盖回去 —— 这是「镜像锁版本优先」
> 的刻意设计。要固定跑某个更低版本，请把 `DSH_IMAGE` 指向锁定该版本的镜像 tag。
>
> 💡 同样的道理：`docker exec dsh rescue dsh-upgrade <版本>` 若装的是比镜像 seed 更低的版本，
> 也会在下次启动时被 seed 覆盖。需要长期停留在某版本，一律以镜像 tag 为准。
>
> ⚠️ 若你仍要手动改 dsh 版本，**建议先升镜像、再升 dsh**：反序会留下「新版 dsh + 旧 entrypoint」
> 的中间状态，而 entrypoint 承担着首启整备（profile manifest 预置、seed 同步、救援工具接线等，
> 见 [07 · 环境变量速查](07-环境变量速查.md) 的安全加固节）。

### 版本号必须写全（不要用 `latest` / `next`）

npm 的 dist-tag 是发布者**手动指定**的别名，**不会自动前进**，三个 tag 可能指向三个不同的版本：

| tag | 本次核对时指向（2026-09-29） | 说明 |
|---|---|---|
| `latest` | `0.1.7-rc.2` | 稳定推荐版 |
| `next` | `0.2.0-rc.2` | 候选版（**本镜像当前锁定的就是它**） |
| `alpha` | `0.1.7-alpha.2` | 预览版 |

> ⚠️ 因此 `npm install -g @deepseek-ai/dsh@latest` **拿到的不是最新版**（当前 latest 是 `0.1.7-rc.2`，
> 最新的 `0.2.0-rc.2` 挂在 `next` 下）。升级时请一律写全版本号：`@0.2.0-rc.2`。
> 装完用 `docker exec dsh dsh --version` 核对。
>
> 📌 上表只是**某一时刻的快照**，dist-tag 由发布者手动指定、随时可能变动 —— 判断"现在指向谁"请以
> `docker exec dsh npm view @deepseek-ai/dsh dist-tags` 的实时输出为准。

> 💡 查当前实际指向：`docker exec dsh npm view @deepseek-ai/dsh dist-tags`。

> ⚠ **升级前先备份**（见 §5 备份）：跨大版本升级可能包含**不可回读**的数据格式变更 —— 例如
> `0.1.2-rc.1 → 0.1.5-rc.1` 会把会话数据升级到 V3，迁移后**旧版本无法再读取**这些会话（原文件保留，
> 但新版格式不被旧版识别）。因此回退 dsh 版本时必须连同 `dsh/` 数据目录一起回滚。
>
> ⚠️ **0.1.7-alpha.1 起会话日志升到 V4（单向）**：V3 会话在**读取时**转换为 V4；一旦打开并继续写入，
> `session-persistence-jsonl` 会发布**当前格式的后继文件**（`session.v4.jsonl.zstd`，原 `session.v3...` 保留不动）。
> 也就是说：升级后发生过写入的会话，**回退到 0.1.6 时读不了** —— 回退必须"版本 + 数据"一起走：
>
> ```bash
> # 升级前（容器内）
> docker exec dsh sh -c "tar czf /data/dsh/backup-sessions-$(date +%F-%H%M).tgz -C /data/dsh sessions storages"
> # 回退（容器内）：先降版本，再用同一份备份覆盖数据，最后重启容器
> docker exec dsh rescue dsh-reinstall
> docker exec dsh sh -c "tar xzf /data/dsh/backup-sessions-*.tgz -C /data/dsh"
> docker restart dsh
> ```
>
> 另：0.1.7 起 `settings.yaml` 由 Settings 服务**一次性导入**到 profile 插件配置，原文件被重命名为
> `settings.yaml.imported`。该变更的完整适配分析属需求/方案类文档，保存在仓库外（不在 GitHub 展示）。
>
> 想留一个可回退的落点，用 `docker exec dsh rescue dsh-upgrade <版本>`：它会先把当前版本记为 last-good。

查看当前版本：

```bash
docker exec dsh dsh --version
```

> 重建镜像的场景：基础环境变化（Node 大版本 / 系统依赖），或想更新镜像内 seed 的 dsh 基础版本：
> `docker build --build-arg DSH_VERSION=<版本> --build-arg APT_MIRROR=mirrors.aliyun.com -t <你的仓库>/dsh-docker-server:<版本> .` 并更新 `.env` 的 `DSH_IMAGE`。
>
> ⚠️ 换了镜像**也不会**自动更新 `/opt/dsh` 卷里的 dsh（seed 只在卷里没有 dsh 时才复制，见本章开头），
> 所以「重建镜像」之后仍要做两步升级的第 2 步。

### 回滚（以镜像 tag 为准）

因为启动时会按版本把 dsh 同步到镜像 seed，**回滚也必须以镜像 tag 为准**：

| 回滚目标 | 操作 |
|---|---|
| 回到旧 dsh 版本 | 在 `.env` 里把 `DSH_IMAGE` 改回旧 tag → `docker compose pull && docker compose up -d`（dsh 会自动跟到该镜像 seed 的版本，无需手动 npm） |
| 临时改 dsh（不换镜像） | `docker exec dsh npm install -g @deepseek-ai/dsh@<版本> && docker restart dsh` —— ⚠️ 仅当该版本 **≥ 镜像 seed** 时才留得住，否则下次启动即被覆盖 |
| **完全回退** | 解压升级前的备份，连 `dsh/` 数据目录一起回滚（见上方数据格式变更的警告） |

> ⚠️「旧版 dsh + 新版镜像」**不再是可行组合**：新版镜像的 seed 会在下次启动把旧版 dsh 顶掉。
> 要停在旧版，必须把**镜像 tag 也一起退回去** —— 这是「镜像锁版本优先」的必然结果。

### 升级后清理残留

长期在容器内升级会累积无人回收的残留，用 `rescue clean` 清理：

```bash
docker exec dsh rescue clean            # 预览（默认 dry-run，不做任何改动）
docker exec dsh rescue clean --yes      # 确认执行
```

清理四项（全部为可证明的垃圾）：

| 项 | 内容 | 说明 |
|---|---|---|
| npm 下载缓存 | `_cacache` | 删后仅需重新下载 |
| pnpm 存储孤儿 | `pnpm store prune` | 官方语义即「只删 unreferenced」 |
| profile 虚拟存储孤儿 | `.pnpm` 中未被 `pnpm-lock.yaml` 引用的条目 | **`pnpm prune` 不会清这些**，是主要的残留来源 |
| 救援历史超限部分 | evidence / incidents | 复用既有 `RESCUE_EVIDENCE_KEEP` / `RESCUE_INCIDENT_KEEP` |

> 🔒 `--yes` 会**先自动拍一份快照**（`reason: pre-clean`）作为回退落点，并**校验它确实存在**后才开始删除。
> 若该快照创建失败、或拍完即被轮转淘汰（例如保留窗口已被占满），`clean` 会**告警并以非零退出，且不删除任何东西**
> —— 宁可不清理，也不在没有可用回退点的情况下删文件。
>
> ⚠ 为满足保留窗口（`RESCUE_KEEP`），拍 pre-clean 快照**可能**按既有轮转策略淘汰最老的**非 pinned** 快照
> （reason 以 `boot-healthy` 开头的快照会被保留，不会被淘汰）。若你手动保留的旧快照因此消失，
> 请在清理前先增大 `RESCUE_KEEP`。
>
> 除上述轮转外，清理**绝不**触碰 `package.json`、`pnpm-lock.yaml`、被引用的 `.pnpm` 条目，
> 因此不影响 `rescue rollback` 的能力。

> ⚠ 若 profile 使用默认的 `hardlink` 快照模式，被快照引用的文件 inode 仍在，
> 空间可能不会立即释放 —— 这是正常现象，待快照被轮转淘汰后回收。

## 2. 安装 / 卸载插件

```bash
docker exec dsh dsh plugin --profile web add <包名>
docker exec dsh dsh plugin --profile web remove <包名>
docker restart dsh
```

插件与数据写入 `/data/dsh` 卷，容器重建/重启不丢。

> ⚠ 插件变更（尤其 update/install）是启动失败的最高频来源。建议用《[06 · 救援模式](06-救援模式.md)》的封装命令装插件（变更前自动快照）；若装坏导致起不来，entrypoint 会自动回退。

## 3. 更换 API 密钥

```bash
# 编辑 .env，修改 DEEPSEEK_API_KEY 后：
docker compose up -d
```

## 4. 查看状态与日志

```bash
docker ps | grep dsh              # 容器状态（healthy / starting / unhealthy）
docker logs dsh --tail 100        # 日志
docker stats dsh                  # 资源占用
```

## 5. 备份

**备份整个部署目录即可**（程序 + 数据 + 配置全在里面）：

```bash
cd <部署目录>        # 含 docker-compose.yml 的目录
tar czf dsh-backup-$(date +%Y%m%d).tar.gz dsh programs workspace .env
```

恢复：把备份解压回原目录，`docker compose up -d` 即可。

> 数据中最重要的是 `dsh/`（DSH_HOME：会话、配置、插件、凭据、Hindsight 记忆库）。
> `workspace/` 是 agent 工作区，按需备份。

## 6. 更新镜像（基础环境变化时）

```bash
docker compose pull        # 拉取新版本 ghcr.io 镜像
docker compose up -d       # 重建容器
```
