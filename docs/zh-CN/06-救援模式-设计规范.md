# DSH Docker 插件救援模式 —— 设计规范

> 日期：2026-09-07 ｜ 目标仓库：dsh-docker-server ｜ 状态：待用户复核
> 关联文件：docker-compose.yml / entrypoint.sh / Dockerfile / .env.example / docs

## 1. 背景与问题

dsh-docker-server 把 DSH 拆成两部分持久化：
- **主程序** /opt/dsh（npm 全局包卷）：日常升级 = npm install -g @deepseek-ai/dsh@版本
- **插件树** $DSH_HOME/profiles/web/（DSH 数据卷内）：cordis.patch.yml（用户层）+ package.json + pnpm-lock.yaml + node_modules/，由 dsh plugin --profile web add/remove 包名 用 pnpm 管理。

现实故障（用户实测）：
- **插件更新/安装是最高频的启动失败来源**（次数远多于主程序升级）。
- 主程序升级只发生过一次，但也是潜在风险。

核心痛点：升级是**就地覆盖唯一的 profile 目录与主程序**，没有保留上一个已知良好（last-known-good）状态；一旦 boot 失败，restart: unless-stopped 导致无限 crashloop，**容器起不来时手动命令根本无机会执行**（否决了纯手动方案 B）。

DSH 主程序本身**无任何内置 rescue/rollback**（已核对 profile-boot 源码），救援逻辑必须建在部署层。

## 2. 目标与非目标

### 目标
- 插件更新/安装后若 boot 失败，**自动回退**到升级前那份能跑的插件树，服务自动恢复，无需人工。
- **数据必须保留**：会话 / 记忆 / 配置 / 凭据一律不动。web 短暂中断（秒级到一两分钟）可接受。
- 主程序升级提供**轻量兜底**（不自动重装全局包，留版本号 + 手动重装命令 + 救生舱）。
- 极端情况（自动回退用尽仍失败）提供**救生舱**：干净最小 profile 起可操作入口。

### 非目标
- 不保证零中断。
- 不自动回退主程序 npm 全局包（连带依赖风险，仅轻量兜底）。
- 不做分布式 / 跨机同步（单机 Docker 部署）。

## 3. 设计概览

三层防线：

```
升级/装插件 -> [第0层] rescue 封装命令：变更前自动快照当前插件树
  |  boot 失败
[第1层] entrypoint 自动回退：有较新的 known-good 就回退 -> 重启 -> 重试(预算内)
  |  回退预算用尽仍失败
[第2层] 救生舱 RESCUE=1：以干净最小 profile 起可操作入口（保留数据）
```

## 4. 快照机制（第 0 层）

### 4.1 快照范围（精确到文件）
插件操作只改动下列文件（已核实），快照只覆盖它们：

```
profiles/web/package.json
profiles/web/pnpm-lock.yaml
profiles/web/pnpm-workspace.yaml
profiles/web/node_modules/             # 快照用 mv + 软链，避免复制 200+ 包
```

**绝不纳入快照 / 绝不回滚**（用户数据，必须原样保留）：

```
profiles/web/cordis.patch.yml           # 用户手工配置层
profiles/web/.dsh-market/
profiles/web/.dsh-module-fallback/
$DSH_HOME/sessions/   $DSH_HOME/storages/
$DSH_HOME/settings.yaml  $DSH_HOME/.credentials.yaml
$DSH_HOME/auth/   （Hindsight 记忆库等）
```

### 4.2 存储位置与轮转
- 快照根：$DSH_HOME/.rescue/（即 /data/dsh/.rescue/）。**必须与 profiles/web 同一文件系统**，mv+软链才廉价且原子（实测 /opt/dsh 与 /data/dsh 在部署仓库中是两个独立挂载目录，可能不同 fs）。回滚只改软链目标，不触及快照自身。
- 命名：snap-0001、snap-0002 … 递增。
- **默认保留最近 3 份**；新快照写入前轮转掉最老超限份。
- 每份快照含 meta.json：时间戳、触发命令、操作前 dsh 版本、操作前插件包清单摘要。
- 快照根维护 last-known-good 指针 = 最近一份“已验证正常”的快照；entrypoint 每次成功 boot 后刷新。

### 4.3 node_modules 快照实现（避免巨量复制）
**默认采用 cp -al 硬链整树快照**：数据块共享、无复制成本、pnpm 视为普通目录，规避 mv+软链与 pnpm hoisted linker 的潜在冲突。回滚=整目录替换。硬链要求快照与源同卷——§4.2 已保证同 $DSH_HOME 卷。
1. 变更前，用 `cp -al profiles/web/node_modules/ $DSH_HOME/.rescue/<snap>/node_modules/` 建硬链快照（同卷才可行）。
2. 元文件 package.json / pnpm-lock.yaml / pnpm-workspace.yaml 直接 cp 入快照。
3. pnpm 变更/安装改写的是 live 的 profiles/web/node_modules（pnpm 以 unlink+create 替换文件，不原地改已硬链 inode，故快照数据块不被污染）。
> mv+软链仅当硬链出问题时作为备选。硬链方案与 pnpm 的实际交互仍须在真实容器内验证（测试策略 §9）。

### 4.4 主程序轻量兜底
- 每次 npm install -g @deepseek-ai/dsh@新版本 前，把当前已装版本写入 $DSH_HOME/.rescue/dsh-version-last-good.txt（全部 rescue 状态集中在 $DSH_HOME/.rescue/ 一处）。
- 提供手动重装命令：rescue dsh-reinstall = 读文件 -> npm install -g @deepseek-ai/dsh@记录版本 -> restart。
- 不做自动回退主程序（连带依赖风险），由救生舱兜底最坏情况。

## 5. entrypoint 自动回退（第 1 层）

### 5.1 判定“起不来”
分层探测与进程崩溃两个信号叠加，避免误判：
1. **分层健康探测**（`scripts/probe-ready.js`，v0.3.7 起）：启动 dsh web 后，给定窗口（默认 120s，.env 可调）内须依次满足 L1 TCP 监听、L2 在其上完成一次 HTTP 往返（**任何状态码均可** —— 装了认证网关时未认证 `GET /` 返回登录页而非应用外壳）、L3 连续 `--stable`（默认 2）次成立；任一未满足即视为未就绪。
2. **进程崩溃**：dsh web 主进程在窗口内直接退出。探针收到 `--pid` 后据此即时判失败，无需等满窗口。
任一成立且**存在更新的 known-good 快照** -> 触发回退。

> 仅在“存在较新快照、且当前启动轮紧跟在一次插件变更后”才回退，避免把普通抖动/非插件启动失败也回退。
>
> **PID1/监督模型变更**：现 entrypoint 末行 `exec dsh web` 把 dsh 当作容器 PID1。自动回退要求 entrypoint 能重启 dsh，故改为**以子进程方式启动 dsh 并监督**（不再 exec），由 entrypoint 承担 PID1 + 存活守护 + 探测 + 回退。dsh 崩溃时由守护重启而非容器退出。

### 5.2 回退循环（带预算）

```
启动 web
  |- 窗口内健康 -> 成功：刷新 last-known-good 指针，常驻
  +- 窗口内失败 且 存在较新 known-good：
       | 回退插件四件套到 last-known-good
       | 重启 web -> 重新探测
       | 若又失败 且 仍有更早快照：再回退一步（预算=可退到 3 份内最旧）
       +- 预算用尽仍失败：停止自动重试，写日志，退出交由 docker restart（避免无限 crashloop 刷日志/掩盖真因）
```

- 每次回退前把“被回退掉的当前状态”保留为新快照（不丢现场，供人工诊断）。
- 回退动作顺序：解除当前软链 node_modules -> 将 live 目录改名为“当前状态”保留快照 -> 把目标 known-good 快照软链回 profiles/web/node_modules -> 恢复对应 package.json/pnpm-lock.yaml/pnpm-workspace.yaml（若它们是常规文件而非软链，先备份当前再回滚）。
- 回退严格只动插件四件套，用户数据不动。

### 5.3 与 compose 关系
- restart: unless-stopped 保留，作为最外层保险；entrypoint 回退预算是主防。entrypoint 自己用 RESCUE_START_TIMEOUT 控制窗口，预算内回退，预算外退出让 docker 策略接管。
- RESCUE_AUTO=off 时 entrypoint 关闭自动回退，仅记录“可回退但已禁用”。

## 6. 救生舱（第 2 层）

### 6.1 触发
- entrypoint 收到 RESCUE=1 环境变量；或第 1 层回退预算用尽后自动以救生舱接管（或提示用户手动 RESCUE=1 重启）。

### 6.2 行为
- 以**不含第三方插件的干净最小 profile** 起最小 web（仅核心 bundle @deepseek-ai/dsh-base + @deepseek-ai/dsh-web-app），绑定同一 $DSH_HOME 数据卷。
- 用户数据（会话/记忆/配置）**原样可读**，只是不加载第三方插件。
- 目的：给用户可操作入口去删坏插件/改 cordis.patch.yml/重装主程序。

> **救生舱机制（已核对 dsh-app-boot 源码定稿）**：新增**独立 profile 目录** `$DSH_HOME/profiles/lifeboat/`，其 `package.json` 的 `dsh.profile.bundles = ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"]`（与官方干净 web 模板 `PROFILE_TEMPLATES.web` 一致），`cordis.patch.yml` 为空 `[]`。DSH 采用**双锚点解析**：核心 bundle 先从 dsh 自身安装解析、后从 profile 目录解析，故干净 lifeboat **无需独立 pnpm install**。用 `dsh --profile lifeboat --port <port> --no-open` 启动，绑定同一 $DSH_HOME。**硬约束：绝不写入/改动现有 `profiles/web/` 与任何用户数据文件；lifeboat 自身产生的会话/记忆独立存于 lifeboat 名下，可事后清理。** 端口分配：正常 web 用 3081，救生舱用 3082（socat 3080 仅转发 3081；救生舱走 3082 直连或另行转发，实现时定稿）。

## 7. 封装命令
容器内 rescue（或宿主机 docker exec dsh rescue ...）：

| 命令 | 行为 |
|---|---|
| rescue snapshot | 变更前手动快照当前插件树 |
| rescue plugin <pnpm args> | = snapshot -> dsh plugin --profile web <args> -> restart |
| rescue rollback [n] | 手动回退 n 步（默认 1）到 known-good |
| rescue dsh-reinstall | 读 dsh-version-last-good.txt 重装主程序到记录版本 |
| rescue status | 列出快照、当前指针、主程序版本、最后事件日志 |
| rescue doctor | 探测 + 只读诊断（不擅自改动） |
| rescue lifeboat | 手动切换为救生舱启动（等价 RESCUE=1） |

.env 提供 RESCUE_AUTO=on/off（默认 on）允许关闭自动回退。

## 8. 错误处理与边界
- 快照写失败不阻断正常升级：记警告继续（自动回退随之降级为“无法回退”，仅记录）。
- 回退本身失败（软链损坏等）：写日志，进入救生舱提示。
- 所有动作落 rescue.log（轮转）。
- **只读诊断优先**：doctor/status 永不改状态；改动只在明确命令或 entrypoint 回退。

## 9. 测试策略
- 容器内“构造坏插件 -> 启动 -> 断言自动回退 + 数据仍在”。
- 测试 node_modules 软链 vs pnpm hoisted linker 兼容性（首要验证点）。
- 测试快照轮转（>3 份最老被删）。
- 测试救生舱在坏插件下能起、用户数据可读。
- 测试主程序轻量兜底：记录版本号 -> 破坏 -> dsh-reinstall 恢复。

## 10. 交付物清单
- entrypoint.sh：自动回退 + 救生舱分支 + last-known-good 刷新
- rescue 脚本（或 scripts/rescue.sh）：命令集
- docker-compose.yml / .env.example：RESCUE_AUTO、RESCUE_START_TIMEOUT、救生舱变量
- Dockerfile：如需要把 rescue 打进 PATH
- 文档：docs/zh-CN/06-救援模式.md + en 版；更新 03/04/README

## 11. 本次已拍板决策
- 触发方式：**自动回退为主**（容器起不来手动无机会，已否决纯手动方案 B）。
- 数据：**必须保留**；web 短暂中断可接受。
- 主程序事故：**轻量兜底**（不自动重装全局包）。
- 快照深度：**默认保留 3 份**。
