# 02 · 认证与远程访问

> [English](../en/02-authentication-remote-access.md) | [简体中文](02-认证与远程访问.md)

**自 v0.6.0 起，认证插件默认就已装好**：镜像内置 [dsh-remote](https://github.com/xgone/dsh-remote)，
首启自动创建一个管理员账号（用户名 `admin`，密码为随机 16 位），密码**只打印一次**在首次启动日志里：

```bash
docker logs dsh 2>&1 | grep -A9 'first-boot admin credentials'
```

拿到密码后访问 `http://<主机IP>:3080` 登录，并尽快在「设置 → 登录与账号」改密 + 开启 MFA。
想要关掉认证层（回到无认证的内网直连模式）见下方 §3。

## 访问方式总览

| 方式 | 安全性 | 适用场景 |
|---|---|---|
| 本机访问（`127.0.0.1:3080`） | 最高 | 部署在同一台机器的浏览器 |
| 内网直连 + 账号登录（**默认**） | 高（账号密码，可选 MFA） | 局域网内使用 |
| SSH 隧道 | 高（加密） | 单人在外临时访问 |
| 反向代理 + HTTPS | 高（认证层 + HTTPS） | 长期远程访问，**有**公网 IP |
| Cloudflare Tunnel | 高（认证层 + Cloudflare 边缘 TLS） | 长期远程访问，**无**公网 IP |

> 浏览器限制：`dsh web` 的部分功能（如 `crypto.randomUUID`、settings）要求**安全上下文**
> （HTTPS 或 localhost）。内网通过 IP 直连时若遇到相关报错，属浏览器安全策略，
> 可用 `localhost` 访问、SSH 隧道或反向代理 HTTPS 解决。

## 1. 默认认证（开箱即用）

镜像内置认证插件并在首启装好，**无需任何手工步骤**。相关行为：

- **账号数据**存于 `$DSH_HOME/auth/store.json`（挂载卷内，容器重建不丢），密码以 scrypt 哈希存储。
- **密码只打印一次**：只在真正创建账号的那一次启动打印。之后重启/重建容器都不会再显示
  —— 避免密码被写进每一次 `docker logs`（日志常被转发、归档、贴进 issue）。
- **★ 密码忘了 / 日志没了：去凭据存档取回**。首启的密码除了打日志，**同时被明文写进**
  `$DSH_HOME/profiles/web/cordis.patch.yml`（权限 0600，仅 root/属主可读），
  所以随时能取回，**不必重置账号**：

  ```bash
  # 宿主机执行（docker exec 默认以 root 运行，能读 0600 文件）
  docker exec dsh grep -A8 'id: remote' /data/dsh/profiles/web/cordis.patch.yml
  ```

  输出里的 `bootstrap.username` / `bootstrap.password` 即初始凭据。首启日志的横幅里也会
  打印这个路径（`stored   : ...`），看到密码的当下就能记下位置。
- **确实要重置**（如存档也被清了）：删除 `<DSH_DATA_DIR>/auth/store.json` 后重启容器，
  会**重新生成**随机密码并打印。
  ⚠ 这会一并清掉所有账号与 MFA 配置。
- **想自己定密码**：在 `.env` 里设 `DSH_ADMIN_PASSWORD=你的密码`（≥6 位）。设了就不打日志
  （适合用密码管理器统一管理）。仅当账号库为空时生效 —— 已有账号时不会被覆盖。
- **想改用户名**：`.env` 里设 `DSH_DEFAULT_ADMIN_USER=你的用户名`（同样只在账号库为空时生效）。

> 原理：entrypoint 在首启把 `bootstrap: {username, password}` 写进
> `$DSH_HOME/profiles/web/cordis.patch.yml`（属主 0600），插件在账号库为空时据此预置首个
> 管理员（role 恒为 `admin`，且是不可删除的 root 账号）。

## 2. 登录并开启 MFA

- 访问 `http://<主机>:3080`，用 `admin` + 首启日志里的密码登录
- 设置 → 登录与账号 → 双重验证（MFA）→ 用 Google Authenticator / 1Password 扫码
- **MFA 必开**：若通过反向代理暴露到公网，认证层是唯一防线

> 首次登录后建议改密（设置 → 登录与账号）。改密后 `cordis.patch.yml` 里的明文 `bootstrap`
> 段即失效（账号已存在时它不再被读取）；如需彻底清除明文，删除该文件里的
> `bootstrap:` 两行即可（保留 `enabled: true`）。

## 3. 关闭认证（回到内网直连）

认证是**默认开启**的。若你的部署只在完全可信的内网（或本机），可以关掉：

```bash
# .env
DSH_SETUP_REMOTE=off
```

```bash
docker compose up -d
```

关闭后：不装插件、不建账号，回到历史行为 —— **完全没有认证层**。此时若用局域网 IP 或域名
访问，必须自行配置 `DSH_TRUSTED_HOSTS`，否则页面能打开但 `/api` 会 403（见 §4）。

> ⚠ 把 `3080` 暴露到公网**又**关掉认证，等于任何人打开页面就得到一个拥有完整 agent 权限的
> 会话（能执行命令、读写工作区）。除非你另有外层认证（VPN / 反代的 auth），否则不要这么做。

## 4. 手工安装 / 升级插件

镜像已内置，一般无需手工安装。需要**换版本或重装**时：

```bash
# 升级到指定版本（插件与账号数据写入 /data/dsh 卷，容器重建不丢）
docker exec dsh dsh plugin --profile web add @xgone/dsh-remote@<版本>
docker restart dsh
```

> 💡 entrypoint 只在 profile 里**没有**该插件时从镜像 seed 复制。你手工升过的版本会被保留，
> 不会被镜像顶回旧版 —— 与 dsh 本体的"seed 只升不降"约定不同（插件升级一律走 `dsh plugin`）。
> 注意 `dsh plugin add` 需要联网（它转发给 pnpm）。

### 配置式 bootstrap（无浏览器场景）

若要在**不打印日志**的前提下预置凭据（例如由部署脚本统一注入密码），除 `DSH_ADMIN_PASSWORD`
外，也可直接编辑 `profiles/web/cordis.patch.yml`（挂载在 `/data/dsh` 卷内）里 entrypoint 写入的
托管块：

```yaml
- id: remote
  config:
    enabled: true
    bootstrap:             # 仅当账号库为空时使用
      username: admin
      password: '一个强密码'
```

> entrypoint 用 `# >>> dsh-docker-server: default auth plugin (managed block ...) >>>` 标记
> 自己写的那一段；**托管块会在每次启动被重写**。要长期自定义，请删掉标记行或改用账号库
> （`enabled` 之外的字段自定义同理）。

## SSH 隧道（单人在外临时访问）

```bash
# 本地端口转发：把远程 3080 映射到本机 3080
ssh -L 3080:127.0.0.1:3080 你的账号@主机IP
# 然后浏览器打开 http://127.0.0.1:3080
```

适合 Windows/Mac/Linux 自带 ssh 的场景，无需额外配置。

## 反向代理 + HTTPS（长期远程访问，推荐）

> ℹ 装了认证插件（默认）时不需要配 `DSH_TRUSTED_HOSTS`：插件的 `trustProxy` 会在请求通过
> 登录认证后，把 Host/Origin 归一为 loopback 再交给 dsh 核心，因此任何域名/隧道 Host 登录后
> 都能正常使用 `/api`（2026-09-17 实测验证）。访问控制由账号密码 + MFA 承担。
>
> 只有**关掉了认证插件**（`DSH_SETUP_REMOTE=off`）而又需要用域名/局域网 IP 直连时，才必须加白：
> 在 `.env` 写 `DSH_TRUSTED_HOSTS=app.example.com`（多个用逗号分隔，可带端口）——否则页面能打开、
> 但 `/api` 会被 403 拒绝（表现为"界面空白 / 连接异常"）。

以 Caddy（自动 HTTPS）为例，Nginx 同理：

```bash
# Caddyfile（域名需解析到主机；80/443 端口开放）
你的域名.com {
    reverse_proxy 127.0.0.1:3080
}
```

> ⚠ 这里的 `3080` 是**宿主机侧**端口，对应 `.env` 的 `DSH_PORT`（默认 3080）—— 改过
> `DSH_PORT` 的话要跟着改。这与下面隧道章节的 Service URL 正好相反：那一段是
> `cloudflared` 容器直连 `dsh` 容器，**容器内**端口恒为 `3080`，不随 `DSH_PORT` 变。
> 两处别记混（详见下方「Cloudflare Tunnel（无公网 IP 场景）」的端口说明）。
>
> ℹ 若 Caddy 与 dsh 同在一个 compose 网络里，也可以写成 `reverse_proxy dsh:3080`
> —— 那属于"容器到容器"一跳，同样恒为 `3080`。

```bash
# 以 Docker 运行 Caddy
docker run -d --name caddy \
  -p 80:80 -p 443:443 \
  -v /path/to/Caddyfile:/etc/caddy/Caddyfile \
  -v caddy_data:/data \
  caddy:2
```

> 反代前务必确认认证插件已启用（默认即是）并开启 MFA（见第 2 节）。

> ⚠ **反代方案的前提是"域名解析到这台主机、80/443 端口对外开放"**。家宽/CGNAT（运营商不给公网
> IP）、或不便做端口映射时，这一节走不通 —— 请改用下面的 Cloudflare Tunnel，它**不需要公网 IP、
> 不需要开放任何入站端口**。

## Cloudflare Tunnel（无公网 IP 场景）

上面的 Caddy 反代有个硬前提：**域名要解析到这台主机，且宿主机的 80/443 端口对公网开放**。
家宽 / CGNAT（运营商不给公网 IP）下这个前提不成立 —— 你既没有可解析的公网地址，也不该为它
在路由器上开端口映射。

Cloudflare Tunnel 换了个方向：由容器里的 `cloudflared` **主动向 Cloudflare 边缘建立出站连接**
（TCP 443），公网请求经 Cloudflare 边缘从这条**已建立的隧道**里回源到容器。全程不需要入站端口，
也不需要宿主机有公网 IP。

```bash
# 一句话概括方向差异
反向代理：公网 ──入站──> 你的主机:443 ──> dsh:3080     ← 需要公网 IP + 开端口
隧道    ：公网 ──> Cloudflare 边缘 ──出站隧道回源──> dsh:3080  ← 不需要
```

> 💰 **Tunnel 本身免费、无需绑卡。** 它是 Cloudflare 的独立产品，**不在 Zero Trust 产品线里** ——
> 如果你在控制台看到要求绑定付款方式，那是 **Access（Zero Trust）** 的页面，不是隧道必需的。
> 这个区分很重要，否则很容易以为自己走错了路（详见下方「可选：加一层 Cloudflare Access」）。

### 与反向代理的对比

| | 反向代理 + HTTPS（Caddy） | Cloudflare Tunnel |
|---|---|---|
| 需要公网 IP | **是** | **否** |
| 需要开放入站端口 | **是**（80/443） | **否**（纯出站 443） |
| 证书/HTTPS 由谁负责 | 你自己（Caddy 自动申请 Let's Encrypt） | Cloudflare 边缘（回源段是明文 HTTP） |
| 域名必须托管在 Cloudflare | 否 | **是**（或至少把该域名接入 Cloudflare） |
| 额外账号 / 费用 | 无 | Cloudflare 账号，**免费** |
| 主要适用 | 云主机、VPS、有公网 IP 的服务器 | **家宽、NAS、CGNAT、内网机器** |

### 启用步骤（2026-10-09 真机实测）

**第 1 步：建隧道、拿 token**

Cloudflare Dashboard → 左侧 **`Networking` → `Tunnels`** → `Create a tunnel` → 选 `Cloudflared`。

> ⚠ 两个容易找错的地方（**新版界面**）：
> - 左侧菜单是 **`Networking`**，不是 `Networks`；
> - Tunnel **不在** `Zero Trust` 菜单下 —— 它是独立产品（这也是它不用绑卡的原因）。

在 `Install cloudflared connector` 这一步，把 **`Select Operating System` 手动切成 `Docker`**，
然后复制 `--token` 后面那串（`eyJ` 开头）。不切的话页面默认给你**浏览器所在系统**的安装包，
那样是**找不到 token 的**。

```bash
# .env
TUNNEL_TOKEN=eyJhIjoi...（粘贴刚才复制的那串）
```

> 🔐 `TUNNEL_TOKEN` 是密钥：确认 `.env` 已被 git 忽略（本仓库默认忽略），并 `chmod 600 .env`。
> token 泄露 = 别人可以把流量引到他自己的源站。

**第 2 步：配路由（这一步坑最多）**

隧道详情页 → **`Routes`** 标签 → `Add a route`。

| 字段 | 填什么 | 为什么 |
|---|---|---|
| 路由类型 | **`Published application`** | 点 `Add a route` 后**必须先选类型**。选 `Private hostname` 是 **WARP 客户端内网通道**，公网访客根本访问不到 —— 症状是"隧道好好的，但域名打不开"。 |
| Domain | 你的域名（如 `dsh.example.com`） | 保存后 Cloudflare 会自动加一条 DNS 记录。 |
| Service → Type | `HTTP` | 回源到容器这一段**是明文 HTTP**，没有 TLS。 |
| Service → URL | **`http://dsh:3080`** | 见下方拆解，**三个部分都不能错**。 |

> ⚠ **新版表单强制要求协议前缀**：只填 `dsh:3080` 会直接报
> `Invalid service URL format (must start with protocol...)`。

`http://dsh:3080` 逐段拆解：

```
  http://  dsh  :3080
  └──┬───┘  └┬┘  └─┬─┘
     │       │     └─ socat 端口。填 3081 会被拒 —— 它只绑容器内回环，跨容器连接根本到不了。
     │       └─ **compose 服务名**。填 localhost / 127.0.0.1 必然 502：
     │          那是 cloudflared 容器自己的回环，跟 dsh 没有半点关系。
     └─ 协议前缀。内网这一段**是 http**：TLS 已经在 Cloudflare 边缘终结了，
        隧道里跑的是明文 HTTP。这里选 https 会 502。
```

> 💡 **一句话记法：内网这一段是 http，外网那一段才是 https。**

> ⚠ **`:3080` 是容器内的端口，与 `.env` 里的 `DSH_PORT` 无关 —— 不要跟着它改。**
> `DSH_PORT` 改的是**宿主侧**映射端口，容器内 socat 恒监听 `3080`（`SOCAT_PORT` 是入口脚本的
> 变量，compose 与 `.env.example` 都不设置它）。云隧道回源走的是 `cloudflared → dsh` 这一跳，
> 端口固定 `3080`；把它改成你的 `DSH_PORT` 值（如 3081）**必然 502**。
> 反之也成立：若你把 `DSH_PORT` 改成别的值，只需按新端口访问宿主，这里**不用动**。

保存后到 **DNS → Records** 核对：应自动出现一条指向 `<Tunnel ID>.cfargotunnel.com` 的 **CNAME**。
**这条记录出现 = 路由配好了**，比翻任何日志都直观。

**第 3 步：启动**

```bash
docker compose -f docker-compose.yml -f docker-compose.cloudflare.yml \
  --profile cloudflare up -d
```

> 📌 文件名是 `docker-compose.cloudflare.yml`，profile 名是 `cloudflare`，服务名是 `cloudflared`
> —— 三者看起来像但**不是同一个东西**，`-f` 后面跟文件、`--profile` 后面跟 profile。
>
> 日常操作建议先定义别名，省得每次重敲两个 `-f`：
>
> ```bash
> DC='docker compose -f docker-compose.yml -f docker-compose.cloudflare.yml --profile cloudflare'
> $DC ps                       # 看状态
> $DC logs -f cloudflared      # 看日志
> $DC stop cloudflared         # 只停隧道，dsh 继续跑
> ```
>
> **不想要隧道**：命令里去掉 `--profile cloudflare` 即可（已在跑的容器需 `$DC down` 收尾）。
> 不带 profile 时 compose 会**完全忽略** cloudflared，连容器都不会创建 —— 这是刻意的"默认不部署"。

**第 4 步：验证**

```bash
# a) 隧道是否注册成功 —— 应看到 4 条
$DC logs cloudflared | grep 'Registered tunnel connection'

# b) 容器之间到底通不通（在 cloudflared 容器里探 dsh）
docker exec dsh-cloudflared wget -qO- --spider --timeout=5 http://dsh:3080/

# c) 公网侧
curl -I https://dsh.example.com/
```

> ⚠ **首次 `up -d` 时 cloudflared 可能要等几分钟才启动**，这是预期行为、不是故障：
> cloudflared 配了 `depends_on: dsh (service_healthy)`，而 dsh 的 healthcheck 带
> `start_period: 300s`（容器首启要复制 seed + 冷启动）。
> 所以 `logs cloudflared` 一直没有输出时，**先看 `ps` 里 dsh 是不是 healthy**。
>
> 之所以不等不行：隧道一注册成功，Cloudflare 就开始把公网流量回源过来；源站还没就绪的话，
> 公网访客看到的是 502 —— 那比"隧道晚几分钟可用"糟糕得多。

### 安全基线（公网暴露前逐条对照）

| 项 | 要求 | 为什么 |
|---|---|---|
| `DSH_SETUP_REMOTE` | **必须保持 `on`**（本仓库默认值） | 这是公网暴露**唯一**的认证防线。关掉它 = 把一台拥有完整 agent 权限的机器挂到公网，任何人打开页面就是一个已登录会话。 |
| MFA（TOTP） | 首次登录后**立刻开启** | 设置 → 登录与账号 → 双重验证。没有 Cloudflare Access 时这是最核心的一道防线。 |
| `DSH_TRUSTED_HOSTS` | **不要填** | 装了认证插件（默认）时，dsh-remote 的 `trustProxy` 会在登录后把 Host 归一为 loopback，隧道域名天然放行（2026-09-17 实测，见本节开头）。填了是多余的。**反过来**：若你把 `DSH_SETUP_REMOTE` 关了，就必须自己填隧道域名，否则 `/api` 403。 |
| `DSH_PUBLIC_URL` | **建议填** `https://<你的域名>/`（结尾带斜杠） | 否则日志与**给模型的系统提示**仍指向容器内 `127.0.0.1:3081`，出现"日志里的链接点不开""模型给的地址打不开"。 |
| `.env` 权限 | `chmod 600 .env` | 内有 `TUNNEL_TOKEN` 与 API key。 |

> ℹ 与反向代理章节同理：**隧道这一段不改变 dsh 的信任模型**。它只负责把流量送进来，
> 访问控制仍然由账号密码 + MFA 承担。

### 可选：加一层 Cloudflare Access

想再加一道门（比如要求邮箱 OTP 才能到达 dsh 登录页），可以启用 Cloudflare Access。

> ⚠ **Access 属于 Zero Trust 产品线，需要绑定付款方式**（免费额度 $0/月、50 用户，但绑卡即授予
> 扣款权限）。**不想绑卡就跳过这一节** —— 它只是"锦上添花"，隧道本身不需要它。
> 别因为看到绑卡页面就以为前面步骤走错了。

**不绑卡的免费替代：WAF 速率限制**（Cloudflare Dashboard → `Security` → `WAF` →
`Rate limiting rules`）。对登录接口做限速，能显著增加暴力破解成本，且完全免费。配置要点：

| 字段 | 建议值 | 理由 |
|---|---|---|
| 匹配 | 路径含 `/api`（或你家登录接口的具体路径） | 只限速认证相关请求，不误伤静态资源。 |
| 速率 | 如 `10 requests / 1 minute` per IP | 正常人不会在 1 分钟内登录 10 次。 |
| 动作 | `Block`（或 `Managed Challenge`） | `Managed Challenge` 对误伤更友好。 |

### 排错

| 症状 | 根因 | 处置 |
|---|---|---|
| 公网 **502**，但日志显示隧道已注册 | **Service URL 填错** —— 最常见的是填了 `http://localhost:3080` 或 `http://127.0.0.1:3080`（那是 cloudflared 自己的回环）、或用 `https://` 回源（内网没有 TLS）、填了 `3081`（只绑容器内回环）、或**把 `3080` 改成了自己 `.env` 里的 `DSH_PORT` 值**（那是宿主侧端口，与容器内 socat 无关）。 | 改成 **`http://dsh:3080`**，三部分逐一核对。 |
| 保存路由时报 `Invalid service URL format (must start with protocol...)` | 新版表单强制协议前缀，你只填了 `dsh:3080`。 | 补上 `http://` → `http://dsh:3080`。 |
| **找不到 `Public Hostname` 标签** | 界面改版了。旧版叫 `Public Hostname`，新版叫 **`Routes`**，语义完全等价。 | 去 `Routes`，`Add a route` 后选 `Published application`。 |
| 左侧菜单里在 `Zero Trust` 下找不到 Tunnels | Tunnel 不在 Zero Trust 菜单下 —— 它是独立产品。 | 走左侧 **`Networking` → `Tunnels`**。 |
| 隧道起来了，但域名打不开 | 路由类型选成了 `Private hostname`（那是 WARP 客户端专用）。 | 改成 `Published application`。 |
| DNS 里没有自动出现 CNAME | 路由没保存成功，或域名不在本 Cloudflare 账号下。 | 回 `Routes` 检查；确认域名已接入 Cloudflare。 |
| **页面能打开，但 `/api` 403**（表现为界面空白/连接异常） | 要么 `DSH_SETUP_REMOTE=off`（此时必须自己填 `DSH_TRUSTED_HOSTS=你的隧道域名`），要么 3080 走的不是认证插件的通道。 | 确认 `.env` 里 `DSH_SETUP_REMOTE=on`（默认），登录后再用 `/api`。 |
| 启动时 cloudflared 立刻退出、日志报 `unauthorized` 或 token 为空 | `TUNNEL_TOKEN` 没填或填错（compose 用 `${TUNNEL_TOKEN:-}` 兜底为空串，**刻意不让 compose 报错**，好让 cloudflared 自己把原因说清楚）。 | `$DC logs cloudflared \| grep -i 'unauthorized\|token'`；回控制台重新复制 token。**dsh 不受影响**。 |
| `logs cloudflared` 长时间没有任何输出 | dsh 还没 healthy，cloudflared 因 `depends_on` 还没启动。 | `$DC ps` 看 dsh 是否 `healthy`；首启等几分钟是正常的（`start_period: 300s`）。 |

> 📌 隧道跑通之后想进一步收紧 cloudflared 容器（只读根 FS + 零 capability），
> `docker-compose.cloudflare.yml` 里 cloudflared 容器已按与 dsh 服务**同级**的硬化运行：
> 只读根 FS + 零 capability + tmpfs `/tmp` + `no-new-privileges`（2026-10-09 真机实测通过）。
> 升级 cloudflared 镜像后若启动失败，按该文件注释里的手法二分定位是"配置错"还是"硬化过度"。

## 安全清单

- [ ] 远程访问时：强密码 + **MFA（TOTP）**
