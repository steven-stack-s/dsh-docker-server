# 06 · 救援模式

> [English](../en/06-rescue-mode.md) | [简体中文](06-救援模式.md)

DSH Docker 的**插件救援模式**：插件更新/安装导致启动失败时，自动回退到最近一个能跑的插件树、服务自动恢复；极端情况下用干净的**救生舱（lifeboat）**提供可操作入口。所有用户数据（会话 / 配置 / 凭据 / 记忆库）全程保留。

> 详细设计见《救援模式设计规范》。该文档属**需求/设计方案类**，不再随仓库发布，保存在仓库外的
> 部署者文档目录：`<仓库同级>/docs/dsh-docker-server/specs/2026-09-07-救援模式-设计规范.md`。
> 本页面向使用者、内容自包含；需要设计取舍的来龙去脉时再查那份文档。

## 1. 设计目标

本仓库把 DSH 拆成两部分持久化：

- **主程序** /opt/dsh（npm 全局包，`npm install -g` 升级）
- **插件树** $DSH_HOME/profiles/web（cordis.patch.yml + package.json + pnpm-lock.yaml + node_modules，由 `dsh plugin` 管理）

**插件更新/安装是最高频的启动失败来源**。一旦 boot 失败，`restart: unless-stopped` 会无限 crashloop，容器起不来时手动命令根本没有机会执行。救援模式为此设三道防线：

| 层 | 作用 | 触发 |
|---|---|---|
| 第 0 层 · 封装命令 | `rescue plugin` 变更前自动快照当前插件树；`rescue dsh-upgrade` 记录 last-good 主程序版本 | 手动执行封装命令 |
| 第 1 层 · entrypoint 自动归因 + 回退 | boot 失败时按确定性规则归因，回退到变更前基线或摘掉肇事插件后重试 | 默认开启（需 `RESCUE_AUTO=on` **且** `RESCUE_SELFHEAL=on`） |
| 第 2 层 · 救生舱 lifeboat | 自动手段都无效时，用干净最小 profile 起一个可操作入口 | **手动** `RESCUE=1`（当前没有自动降级，见下方注） |

> 注：**"自动进救生舱"尚未实现**（早期版本的本表曾写作"自动降级"，属文档与实现不符，已更正）。
> 自动手段与预算都用尽仍失败时，entrypoint 会退出，由 `restart: unless-stopped` 反复重试；要进救生舱
> 请手动在 `.env` 设 `RESCUE=1` 后 `docker compose up -d`（见 §5）。

## 2. 如何启用

救援能力默认**已开启**，无需额外配置：

1. 镜像需包含救援工具集（`/opt/dsh-rescue` 与 `rescue` 命令），由本仓库 Dockerfile 打包。若你的容器较旧、`docker exec dsh rescue status` 报 command not found，请拉取较新镜像并重建容器：
```bash
docker compose pull && docker compose up -d
```
> 自建镜像的用户：先 `docker build --build-arg DSH_VERSION=<版本> -t <你的tag> .`，再把 `DSH_IMAGE` 指向该 tag。compose **刻意不提供本地构建路径**（原因见 `docker-compose.yml` 顶部注释：`image:` 与 `build:` 同名会让"pull 不到"静默退化成跑旧代码）。
2. 数据卷无需迁移——快照存于 DSH 数据卷内（见 §6）。

相关环境变量（`.env`；容器内可用 `docker exec dsh env | grep RESCUE` 查看）：

| 变量 | 默认 | 说明 |
|---|---|---|
| RESCUE | 0 | 0=正常；1=救生舱启动（见 §5） |
| RESCUE_AUTO | on | **自动干预总闸**：on=失败时自动归因并回退 / 摘插件；off=只诊断 + 写 incident，绝不自动改动插件树 |
| RESCUE_SELFHEAL | on | on=允许自动摘插件 / 回快照；off=只诊断 + 写 incident（与 RESCUE_AUTO 取与，任一为 off 都不自动改） |
| RESCUE_START_TIMEOUT | 120 | 单轮启动就绪探测超时（秒） |
| RESCUE_KEEP | 3 | 保留的最近**快照**份数（最新一份 `boot-healthy` 基线被钉住、不参与轮转，见下「快照保留」） |
| RESCUE_MAX_ATTEMPTS | KEEP+1 | 启动重试上限（与快照保留数解耦；不设则跟随 `RESCUE_KEEP`） |
| RESCUE_EVIDENCE_KEEP | KEEP | 证据目录（`evidence/boot-*`）保留份数（不设则跟随 `RESCUE_KEEP`） |
| RESCUE_PROFILE | web | 回退 / 插件操作目标 profile |
| RESCUE_REMOVE_LIMIT / RESCUE_ROLLBACK_LIMIT | 2 / 2 | 自愈预算：窗口内自动摘插件 / 回快照的次数上限（见 §4b） |
| RESCUE_SELFHEAL_WINDOW | 86400 | 自愈预算的滑动窗口（秒）：窗口过期自动清零，避免预算永久耗尽后自愈静默失效 |
| RESCUE_SNAPSHOT_ON_HEALTHY | on | 确认健康后自动拍一份基线快照（为绕过 rescue 封装的变更留回退点） |
| RESCUE_SNAPSHOT_MODE | hardlink | 快照模式：`hardlink`=`cp -al`（省空间，但与 live 共享 inode，靠 `rescue verify` 检测污染）；`copy`=`cp -a` 独立不可变副本 |
| RESCUE_AUTO_LIFEBOAT | on | 自愈彻底失败后是否自动降级进救生舱（一次性标记，下次启动生效） |
| SOCAT_MAX_CHILDREN | 64 | socat 并发连接上限（fork 模式每连接一个进程，无上限时可耗尽容器内存） |
| DEEPSEEK_API_KEY_FILE | （空） | 从文件读取模型密钥（docker secret / 挂载文件），优先级高于 `DEEPSEEK_API_KEY`，避免密钥出现在 `docker inspect` 里 |

## 3. 命令速查

在宿主机上用 `docker exec dsh rescue ...` 操作（容器内也可直接 `rescue ...`）：

| 命令 | 行为 |
|---|---|
| `docker exec dsh rescue status` | 查看快照列表、当前指针、DSH 版本、最后事件日志、上一轮启动输出是否落盘（只读）。**救生舱里会额外打印 `LIFEBOAT MODE` 行动指引** |
| `docker exec dsh rescue snapshot` | 手动为当前插件树拍快照（作为回退目标） |
| `docker exec dsh rescue doctor` | 只读诊断：profile 目录与 package.json、快照列表、evidence/state/incident 目录健康、上次运行状态、**上一轮启动输出尾部**（救生舱里另打 `LIFEBOAT MODE` 指引） |
| `docker exec dsh rescue plugin add <包名>` | 先自动快照、再执行 `dsh plugin --profile web add <包名>`（装前先留回退点） |
| `docker exec dsh rescue plugin remove <包名>` | 同上，用于卸载插件 |
| `docker exec dsh rescue snapshots` | 快照清单：编号 / 创建时间 / 模式 / **与当前插件树是否相同** / 变更原因。直接回答"哪个快照还能用" |
| `docker exec dsh rescue verify [快照]` | 快照完整性校验：meta 的 node_modules 树哈希与重算值是否一致（`hardlink` 模式下快照可能被就地改写污染）；不带参数则校验全部 |
| `docker exec dsh rescue rollback` | 手动回滚，**自动跳过与当前插件树内容相同的快照**（自愈拍的"故障现场"就属于这类），打印提示后需 `docker restart dsh` |
| `docker exec dsh rescue rollback --to <快照>` | 显式指定回滚目标；目标与 live 相同会直接拒绝，不做无意义的"恢复" |
| `docker exec dsh rescue rollback --dry-run` | 只打印将恢复到哪个快照，不改动任何文件 |
| `docker exec dsh rescue selfheal status` | 查看自愈总闸与预算余额（removes/rollbacks 已用多少、窗口何时重置） |
| `docker exec dsh rescue selfheal reset` | 手动清零自愈预算，立即恢复自愈能力 |
| `docker exec dsh rescue export [路径]` | 打包诊断材料（事故 / 状态 / 快照元数据 / 环境摘要 / doctor / 最近启动日志尾部）成一个 tar.gz，供求助或提 issue；**不含**插件树、会话、记忆与任何密钥 |
| `docker exec dsh rescue lifeboat on\|off\|status` | 手动请求 / 取消 / 查看"下次启动进救生舱"的标记（自愈耗尽时会自动置位） |
| `docker exec dsh rescue dsh-upgrade <版本>` | 记录当前 DSH 版本为 last-good，再升级主程序到指定版本 |
| `docker exec dsh rescue dsh-reinstall` | 按记录的 last-good 版本容器内重装主程序（主程序事故时的轻量兜底） |
| `docker exec dsh rescue lifeboat` | 打印切换到救生舱的操作指引（等价 RESCUE=1） |
| `docker exec dsh rescue report` | 总览最近事故（incident）表：phase / 根因类别 / 肇事插件 / 自愈 outcome（见 §4b） |
| `docker exec dsh rescue report <id>` | 展开单条 incident 全字段（rationale / 自愈动作 / evidenceRef / redline 断言） |
| `docker exec dsh rescue report --json` | 输出 incidents 的合法 JSON（供脚本消费） |
| `docker exec dsh rescue incident list` | 列出已记录 incident 的 id |
| `docker exec dsh rescue snapshot --reason '<text>'` | 手动快照并带触发上下文（如 `--reason 'plugin add @scope/x'`），供后续归因 |
| `docker exec dsh rescue clean [--yes]` | 升级后清理残留（默认 dry-run 预览；`--yes` 执行并先拍快照）。含 `TMPDIR` 下 dsh 临时产物的回收（见 §4c） |

> 安装/卸载/回退插件后，用 `docker restart dsh` 让 entrypoint 以新插件树启动；若启动失败，entrypoint 会自动回退（见 §4）。

> 注：`dsh-upgrade` / `dsh-reinstall` 是 `rescue` 的子命令，完整命令为 `docker exec dsh rescue dsh-upgrade <版本>` 与 `docker exec dsh rescue dsh-reinstall`。

## 4. 自动回退机制（entrypoint）

重启时 entrypoint 以**子进程**方式启动 dsh web，并对容器内 127.0.0.1:3081 做**分层就绪探测**（`probe-ready.js`），最多等 `RESCUE_START_TIMEOUT`（默认 120s）。判定“起不来”= 窗口内未满足全部层级：L1 TCP 未开始监听、L2 连上了却拿不到任何 HTTP 响应、或 L3 未连续 `--stable`（默认 2）次成立；另外自 v0.3.7 起探针会收到 `--pid`，dsh 主进程一消失即立即判失败，无需等满窗口。

回退流程：

1. 启动失败 → 先由 `diagnose.js` 按确定性规则归因（§4b），给出 `remove-plugin` / `rollback` / `report-only`；
2. **执行任何自愈动作前**先过总闸：`RESCUE_AUTO` 与 `RESCUE_SELFHEAL` 必须**同时**为 `on`，否则只写 incident（report-only）；
3. `rollback` 会把插件树（package.json / pnpm-lock.yaml / pnpm-workspace.yaml / node_modules）还原到目标快照并**重试**启动（最多 `RESCUE_KEEP+1` 次）；
4. 无诊断能力 / 无证据时退化为旧兜底：`RESCUE_AUTO=on`、存在快照、且其指纹与 live 不同（指纹 = package.json + pnpm-lock.yaml 的哈希）时回滚最新快照；
5. 自动手段都无效 / 预算用尽 → 退出，交由 `restart: unless-stopped` 重试；需**人工** `RESCUE=1` 进救生舱（§5）。

boot 成功后 entrypoint 会持续等待 dsh；若此后 dsh 崩溃，容器退出，由 Docker 重启策略接管。回退是否发生可看日志：

```bash
docker logs dsh --tail 100 | grep -iE 'rollback|healthy|rescue'
```

**审计日志**。除了容器日志，所有救援事件也会追加写入数据卷内一个文件——**`$DSH_HOME/.rescue/log/rescue.log`**（宿主机默认 `./dsh/.rescue/log/rescue.log`），即使容器日志丢失也能离线审计救援历史。内容含手动 `snapshot` / `restore apply|done` / `prune`，以及 entrypoint 现在记录的事件：

```bash
tail -20 /data/dsh/.rescue/log/rescue.log      # 容器内执行
# 例如 2026-09-07T17:12:00+0800 snapshot created snap-0001 (reason: plugin add @scope/x)
#      2026-09-07T17:12:05+0800 selfheal rollback to snap-0001      # 此行在 docker logs（elog）
#      2026-09-07T17:12:05+0800 restore apply snap-0001 -> /data/dsh/profiles/web
#      2026-09-07T17:12:08+0800 restore done snap-0001
#      2026-09-07T17:12:08+0800 selfheal rollback ok: snap-0001
#      2026-09-07T17:12:30+0800 baseline snapshot on healthy: snap-0002
#      2026-09-07T17:13:00+0800 boot exhausted; exit for docker restart policy
```

`rescue status` 显示的“最后事件日志”即该文件尾部。

## 4b. 自动排查 · 根因归因 · 智能自愈（rescue-diagnose）

在「自动回退」之上，entrypoint 提供**证据驱动的归因 + 智能自愈闭环**：启动失败 / 运行期崩溃时把每轮 dsh 启动输出 tee 捕获到证据目录，按**确定性规则**（非 LLM）归因根因，按决策矩阵自动处置，并把每次事故写成可审计 incident，用 `rescue report` 人读呈现。全程**严守红线**：只动插件树四件套（package.json / pnpm-lock.yaml / pnpm-workspace.yaml / node_modules）与 `$DSH_HOME/.rescue` 下的状态/incident，**绝不自动改** `cordis.patch.yml`、会话 / 记忆 / 配置 / 凭据。

**触发路径**

1. **boot 失败**（探测超时 / 子进程早退）：捕获该轮证据 → 调 diagnose 归因（读证据 + 审计 + 快照 meta 的 trigger/reason）→ 按 `recommendedHeal` 处置：`remove-plugin`（先快照现场，再经 `dsh plugin remove` 摘肇事插件，只动四件套）/ `rollback`（回退到变更前基线快照）/ `report-only`（不自动改，写 incident 提示）→ 写 incident 后重试或退出。

> **边界（真机实测）**：`remove-plugin` 经 `dsh plugin remove` 只清 `package.json` 的 `dependencies`，**不清 `dsh.profile.bundles`**（bundles 是 profile 插件组合声明，非 pnpm 依赖）。因此它仅对「依赖型插件故障」有效；对 **bundles 条目型启动故障**（如坏 bundle 引用导致无法解析），`dsh plugin remove` 会因「project has no dependencies」失败——该自愈会如实记录 `action outcome=fail` 并降级为 `report-only`（红线不破）。这类故障的**可靠自愈是 `rollback`**（回退到变更前基线）。诊断矩阵：offender = 最近新增（依赖型）→ `remove-plugin`；bundles 组合故障 → 交 `rollback` 兜底。
2. **运行期崩溃**：dsh healthy 后异常退出 → 写 last-run（abnormalExit）并退出（沿用 docker restart 交接，不在 PID1 内无限拉起）；下次启动读到异常 → 记录 runtime incident，用 `rescue report` 复核。**保守默认：运行期崩溃仅自动报告归因，不自动摘/回退**（避免把无关崩溃误伤），由人工按报告处置。

**自愈护栏**（防无限 / 防误伤）：

- 自愈预算写 `state/selfheal.json`：**窗口内**自动摘插件 ≤ `RESCUE_REMOVE_LIMIT`、回快照 ≤ `RESCUE_ROLLBACK_LIMIT`，超限转 report-only；窗口（`RESCUE_SELFHEAL_WINDOW`，默认 24h）过期后计数自动清零、自愈能力恢复。用 `rescue selfheal status` 看余额、`rescue selfheal reset` 立即重置。
- 回滚目标必须"有意义"：与当前插件树指纹相同的快照（典型是刚拍的故障现场）会被跳过，避免"回滚了但什么都没变，还记成 rollback ok 并消耗预算"。
- 归因保守（宁报告勿错拆）：仅当证据日志命中插件失败且肇事插件 = 最近一次新增时才 `remove-plugin`；其余优先回基线或只报告。
- 每次自愈动作前先快照现场；全部动作写 `rescue.log` + 更新对应 incident。
- `RESCUE_SELFHEAL=off` 时只诊断 + 写 incident + 提示，绝不自动改。

**证据与事故落盘**（都在数据卷 `$DSH_HOME/.rescue/` 下）：

- `last-web-boot.log`：**最后一轮** web 启动的输出（覆盖式），进救生舱后靠它看根因（见 §5b）。
- `evidence/boot-<seq>-<ts>/`：每轮启动的 dsh 输出（dsh.log）+ 临时件。
- `incidents/inc-<ts>-<rand>.json`：一次事故的归因 + 自愈动作 + redline 断言；保留 `RESCUE_INCIDENT_KEEP`（默认 20）份。
- `state/last-run.json`、`state/selfheal.json`：最近运行状态 / 自愈预算。

**快照可信度**（本次改动起，尚未发版）：快照 meta 记录 `profile` / `mode` / `treeHash`（node_modules 树指纹，不跟随符号链接）。
默认的 `hardlink` 模式用 `cp -al`，秒级且几乎不占空间，但快照与 live **共享 inode** —— 任何"就地改写"（append / `sed -i` / 原生模块重编）会同时改坏历史快照。因此建议：

```bash
docker exec dsh rescue snapshots        # 看各快照与 live 的差异
docker exec dsh rescue verify           # 检查快照是否已被写坏（非 0 = 有不可信快照）
```

若 `verify` 报某个快照已被写坏，就不要再回滚到它，改用更早的可用快照；把 `RESCUE_SNAPSHOT_MODE=copy` 设为 `copy` 可让后续快照成为真正不可变的独立副本（代价是 node_modules 全量复制）。

**快照保留**。超过 `RESCUE_KEEP` 时逐出最老的快照，但**最新一份 `boot-healthy` 基线被钉住、不参与轮转**：
自愈选回退目标时第一轮只认基线（`rescue_pick_rollback_target`，唯一被证明能启动过的状态），而插件市场（dshmarket）/
手工变更会连续产生快照 —— 纯 FIFO 轮转会先把基线删掉，自愈就只能退化到第二轮的「任意非现场快照」。
钉住只改变**淘汰谁**，总份数仍受 `RESCUE_KEEP` 约束：例如 `RESCUE_KEEP=2` 且窗口内是「1 份最老基线 + 2 份市场变更快照」时，
淘汰的是次老的变更快照，基线留下；窗口内全是基线时照常逐出更旧的那些（不会卡住）。

查看某次事故：`docker exec dsh rescue report <id>`；示例输出含 `rootCause.rationale`（为什么这么判）与 `redline.cordisPatchTouched=false`（本轮未触碰 cordis.patch.yml 的断言）。
> 真机校准提示：归因用的日志模式表在 `/opt/dsh-rescue/diagnose.js` 顶部 `PLUGIN_FAIL_PATTERNS`（可调数据常量）。判定顺序是"**先**看日志是否命中插件失败模式，**再**从日志里提取肇事包名"——因此只打印过包名、但并非插件故障的日志不会被误判成插件问题。若某类真实失败未被命中而误判 report-only，可在宿主上用 `docker exec dsh rescue report <id>` 回看 evidence 后手动调参一次。

## 4c. 临时文件回收（rescue clean）

**背景**：`read_only: true` 让 `/tmp` 只能用 tmpfs，而它是**内存硬上限**（本仓库取 128m）。dsh 做**临时任务 / 验证测试**时会把三类产物写进 `os.tmpdir()`：

- 工具输出溢出（读大文件、大范围搜索的结果）
- 被托管命令的输出 spool（构建 / 测试的输出动辄几十上百 MB）
- 工作区变更捕获

单次大输出就能撞满 128m。更麻烦的是 dsh 自身的回收都不可靠：溢出文件只在**启动时**扫一次、且默认只清 30 天前的；命令 spool 只在进程退出时 `rmdir`（非空目录删不掉，上游注明要等"external cleanup"）。于是产物只增不减。

**对策**：`TMPDIR` 默认指到数据卷 `/data/dsh/tmp`（见《[07 · 环境变量速查](07-环境变量速查.md)》），空间上限从"128m 内存"变成宿主机磁盘；回收交给：

```bash
docker exec dsh rescue doctor          # 只读：看当前 TMPDIR 与 dsh 临时目录数量
docker exec dsh rescue clean           # dry-run：列出将回收的陈旧目录（不动任何文件）
docker exec dsh rescue clean --yes     # 执行回收
```

**安全边界**（只删这些，其余一律不动）：

- 只删 **dsh 自建目录名单**内、且名字形如 `mkdtemp`（前缀 + 恰好 6 位字母数字）的一级目录：
  `dsh-spill-*` / `dsh-subprocess-*` / `dsh-subprocess-launch-*` / `dsh-workspace-changes-*` / `dsh-shell-*`。
- **不删** `dsh-office-to-pdf-*`、`dsh-open-in-app-*`、`libreoffice-kit-*` 等转换中间产物（可能正在使用），也不动任何你放在 `TMPDIR` 里的东西 —— 宁可少删，绝不误删。
- 只删**陈旧**的：默认保留 `RESCUE_TMP_KEEP_MIN`（1440 分钟 = 24h）内被写过的目录，视为"可能仍在使用"。

> 迁移前提示：`TMPDIR` 一旦从 `/tmp` 移走，`/tmp` 下**已遗留**的 `dsh-*` 目录不会再被任何人扫描（dsh 的清理基准也跟着 `TMPDIR` 走）。首次切换前先手动清一次：
> ```bash
> docker exec dsh sh -c 'rm -rf /tmp/dsh-spill-* /tmp/dsh-subprocess-* /tmp/dsh-workspace-changes-* /tmp/dsh-shell-*'
> ```

## 5. 救生舱（lifeboat）

插件树坏到自动回退也救不回来时，用**干净最小 profile** 起一个不含第三方插件的 web（仅 DSH 核心），仍绑定同一 `$DSH_HOME`——用户数据原样可读、只是不加载坏插件，方便你删坏插件 / 改 cordis.patch.yml / 重装主程序。

进入救生舱：

```bash
# 编辑 .env：把 RESCUE 设为 1，再重建容器
RESCUE=1
docker compose up -d
```

救生舱启动后仍通过外部 3080 访问（容器内 socat 把 3080 转发到 3081 的 lifeboat）。此时可用 `docker exec dsh` 执行维护命令（删坏插件、改配置）。

退出救生舱恢复正常：

```bash
# 编辑 .env：把 RESCUE 设回 0，再重建容器
RESCUE=0
docker compose up -d
```

> 救生舱硬约束：绝不改动现有 `profiles/web/` 与任何用户数据文件；lifeboat 自身产生的会话/记忆独立存于 `profiles/lifeboat` 名下，可事后清理。

### 5b. AI 自助修复流程（在救生舱里怎么干活）

救生舱的设计目标就是"让人（或 AI）能在界面里把问题修好，再回到正常 profile"。容器内的 AI 常常在这里空转：它**无法自行回到正常 profile**，因为 `RESCUE=1` 是**容器环境变量**（容器内改不了）、`.env` 在宿主机未挂载、容器内也没有 docker socket（安全设计，不破坏）。若它去 `kill` PID1，`restart: unless-stopped` 拉起后读到的仍是 `RESCUE=1`，只会再次进救生舱 —— 白白循环。

正确流程：

```text
① 确认自己在救生舱         rescue status          # 输出 LIFEBOAT MODE 指引块
② 看上一轮到底为什么挂      rescue doctor          # 回显 last-web-boot.log 尾部
③ 修复 profiles/web（卸坏插件 / 改 package.json 等）
④ 明确告知用户去宿主机执行  docker restart dsh
```

关键点：

- **`rescue status` / `rescue doctor` 在救生舱里会打印一段 `LIFEBOAT MODE` 行动指引**，直接给出上面第 ④ 步要用户执行的命令。AI 读到它就该停止尝试重启，转而通知用户。
- **不要 `kill` PID1、也不要在容器内想办法重启容器**：重启后仍是救生舱，问题不会消失。
- 回到正常 profile 的唯一入口在宿主机：
  ```bash
  docker restart dsh                       # .env 里 RESCUE=0 时
  sed -i 's/^RESCUE=.*/RESCUE=0/' .env && docker compose up -d   # .env 里 RESCUE=1 时
  ```

**崩溃证据落盘（`last-web-boot.log`）**。进救生舱后原 dsh 进程已死，而容器内既无 docker socket 也读不到 `docker logs` —— 真实根因（例如 `Cannot find module 'xxx'` 的堆栈）本来看不着。因此 entrypoint 的监督循环会把**每一轮** web 启动的输出覆盖式写入：

```text
$DSH_HOME/.rescue/last-web-boot.log      # 宿主机默认 ./dsh/.rescue/last-web-boot.log
```

- 覆盖式（每轮 attempt 一轮），不会无限增长；始终保留**最后一轮**的内容。
- 每轮启动失败时，容器日志（`docker logs dsh`）里还会额外回显一段 `last boot output (tail):`（默认末 80 行），便于不看文件也能定位。
- 救生舱不写这个文件（`boot_lifeboat` 直接 `exec`，走容器 stdout），所以文件内容永远是**最后一次 web 启动失败**的输出。
- 注意：该文件以 dsh 的 **stderr** 为主（崩溃堆栈、模块解析失败等都走 stderr）；stdout 仍完整进证据链 `evidence/boot-*/dsh.log` 与 `docker logs`。

**自动降级**：当自愈动作与预算都耗尽仍起不来时，entrypoint 会写一个**一次性**标记并退出；下一次启动即以救生舱 profile 起来（进入时清除标记），这样用户至少能进界面处置，而不是对着无限 crashloop。修好插件后直接 `docker restart dsh` 就回到正常 profile。不想自动降级的部署可设 `RESCUE_AUTO_LIFEBOAT=off`。

## 6. 关闭方法 / 备份提示

**关闭自动干预**：把 `.env` 的 `RESCUE_AUTO=off`（或 `RESCUE_SELFHEAL=off`）后 `docker compose up -d`。两者**任一**为 off，启动失败都只诊断 + 写 incident，**不会自动改动插件树**，然后退出交由 `restart: unless-stopped` 反复重试。排查插件问题期间建议临时设为 off。

**完全停用救援模式**：封装命令本身是手动工具无法关闭；把 `RESCUE_AUTO=off` 与 `RESCUE=0` 即回到“不自动干预”的普通部署。

**备份提示**：救援快照位于 DSH 数据卷内 `$DSH_HOME/.rescue`（宿主机默认 `./dsh/.rescue`），随 `dsh/` 一起被备份——按《[03 · 升级与维护](03-升级与维护.md) §5 备份》备份整个部署目录即可，无需单独处理。快照与回退**只动插件四件套**，永不触碰会话 / 记忆 / 配置 / 凭据。

## 7. 故障排查入口

- 容器起不来 / 反复 crashloop → 先看 `docker logs dsh --tail 100` 是否有 `selfheal rollback to` / `no-evidence fallback: rollback to` / `booting clean lifeboat profile` 标记，再用 `docker exec dsh rescue report` 看归因，并结合《[04 · 故障排查](04-故障排查.md)》定位。
- 需在真实 Docker 宿主机端到端验收救援链路 → 运行仓库内脚本 `scripts/t/e2e-rescue-on-host.sh`（会短暂重启 dsh 容器，见脚本头注释）。
