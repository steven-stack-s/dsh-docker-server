> 升级对象：`dsh-docker-server` 的 `ARG DSH_VERSION`，从 `0.2.1-alpha.3` → `0.2.1-alpha.4`

## 二、包级变化（实测）

隔离安装对照：alpha.3 = **303** 包，alpha.4 = **304** 包。

### 2.1 新增 4 个包

```
dsh-client-ui-plugin-market
dsh-experimental-plugin-market-bundle
dsh-plugin-market
dsh-plugin-market-index
```

### 2.2 移除 3 个包

```
dsh-client-store
dsh-client-ui-primitives
dsh-client-ui-slots
```

### 2.3 净变化

`303 + 4 − 3 = 304` ✓（与实测包数一致）

### 2.4 新增包的归属与默认状态（关键核查）

上游新增的是一个**可选**的「插件市场」子系统。核查结果：

| 包 | 在 `dsh-base` patch 中 | 在 `dsh-web-app` patch 中 | 本项目会装载？ |
|---|---|---|---|
| `dsh-plugin-market` | ✗ | ✗ | **否** |
| `dsh-plugin-market-index` | ✗ | ✗ | **否** |
| `dsh-client-ui-plugin-market` | ✗ | ✗ | **否** |
| `dsh-experimental-plugin-market-bundle` | ✗ | ✗ | **否** |

`dsh-experimental-plugin-market-bundle/cordis.patch.yml` 内容：

```yaml
# Custom plugin markets: the Host service that reads the index sources the
# user configures and the Web Discover tab of the Plugins page. The
# `plugin_market` tool row in the Creator preset registers its tool only
# while this service is mounted.
- insert:
    - id: plugin-market
      name: '@deepseek-ai/dsh-plugin-market'
      disabled: !!js "!ctx.get('profileContext')"
    - id: ui-plugin-market
      name: '@deepseek-ai/dsh-client-ui-plugin-market'
```

**本项目 profile 只列 `@deepseek-ai/dsh-base` + `@deepseek-ai/dsh-web-app`（见 `scripts/entrypoint.sh`
的 web profile 预置块），不包含该 experimental bundle，故这 4 个包虽被安装进依赖树，但不会装载。**

### 2.5 项目对增删包的引用数

全仓 grep（排除 `.git`、`docs/analysis`）：

| 包 | 项目引用文件数 |
|---|---|
| 4 个新增包 | **全部 0** |
| 3 个移除包 | **全部 0** |

**结论**：移除的 3 个包在本项目零引用，移除无影响；新增的 4 个包本项目零引用且不装载。

## 四、渲染配置精确对照（核心证据）

两版分别以本项目真实 profile 定义渲染（`dsh web --dump-config`，bundles = `dsh-base` + `dsh-web-app`）：

**零移除**。

### 4.2 全量 diff

### 4.3 新增行的默认状态（关键）

| 位置 | 状态 |
|---|---|

**结论：能力面零变化。**

## 五、本项目核心耦合点：认证插件注入链路

这是本项目真正的耦合点，每次升级都必须端到端验证。

### 5.1 注入方式（与项目真实实现一致）

1. profile manifest 的 `bundles` 追加 `@xgone/dsh-remote`
2. profile 的 `cordis.patch.yml` 写 `- id: remote` 覆盖 `config`（`scripts/remote-setup.sh`
   的 `_rs_write_remote_row` 托管块）

### 5.2 渲染结果对照

两版注入后渲染，提取 `- id: remote` 插件段：

| 版本 | 段行数 | 段字节数 |
|---|---|---|
| alpha.3 | 8 | 163 |
| alpha.4 | 8 | 163 |

`diff` → **逐字节完全一致**：

```yaml
- id: remote
  name: '@xgone/dsh-remote'
  config:
    enabled: true
    bootstrap:
      username: admin
      password: <redacted>
# == @xgone/dsh-remote
```

### 5.3 真实启动 + HTTP 认证边界

两版各自真实启动（配 bootstrap 凭据）：

| 版本 | 启动 | 打印 token | 登录页 | 未认证 API |
|---|---|---|---|---|
| alpha.3 | ✓ | ✓ | 200 | 403 |
| alpha.4 | ✓ | ✓ | 200 | 403 |

**两版行为完全一致。**

### 5.4 区分：`remote-access` vs `id: remote`

⚠ 上游自 alpha.3 起有 base 条目 `remote-access`（`@deepseek-ai/dsh-api-remote-access`，
非 owner Peer 的方法级访问控制），与本项目注入的 `id: remote`（`@xgone/dsh-remote` 认证插件）
是**两个不同的东西**，勿混淆。`remote-access` 在渲染中为独立条目，owner 永不被检查，
单用户容器部署无行为影响。

## 八、验证边界（诚实说明）

### 8.1 已完成的验证

1. 两版隔离安装，包级精确对照（`comm`）
2. 两版渲染配置全量 diff
3. 两版注入认证插件后渲染，插件段逐字节对照
4. 两版真实启动 + HTTP 认证边界探测
5. 真机构建 `dsh-alpha4:test`，镜像内 seed / pnpm / 插件版本自证
6. 真机全硬化启动（只读根 FS、cap-drop、no-new-privileges、三卷）
7. 真机全量门禁 39/39 PASS
8. 真机 e2e 容器自检 PASS

### 8.2 未覆盖 / 环境限制

- **本地沙箱**：22 项门禁失败，原因是 `/data/dsh` 不可写、缺 `node` —— 已用 `git stash`
  在**未改动代码**上复现同样失败，确证是环境限制而非本次改动引入。真实结论以真机 39/39 为准。
- **`mem_limit` / `cpus` 未应用**：验证机为嵌套 DinD（cgroupv2 threaded 模式），无法施加
  内存/CPU 限额。与历次升级一致，不构成本次特有缺口。
- **`e2e-rescue-on-host.sh` / `e2e-rescue-diagnose-on-host.sh` 未执行**：脚本头部明确要求
  「宿主机上已有健康 dsh 容器」并会短暂中断 web、可能污染宿主现场，不适于在验证机执行。
  已在真机执行的是自建临时容器的 `e2e-container-selftest.sh`。
- **多架构 arm64 未在真机验证**：真机为 amd64。arm64 由 CI 构建产出，未在真机运行。

### 8.3 结论的可信范围

上述「能力面零变化」的结论**基于渲染配置对照**（这是 DSH 判定实际装载哪些条目的权威输出），
以及**真实启动 + HTTP 边界实测**。未对全部 289 个变动包做逐行代码审计 —— 那既不必要
（上游统一发版）也不可行。若上游存在仅在高负载/长会话下才显现的行为变化，本次验证**不覆盖**。
