## 一、版本存在性与 dist-tag 实测

npm dist-tags（2026-10-15 实测）：

| tag | 指向 | 说明 |
|---|---|---|
| `latest` | `0.2.0-rc.2` | 稳定推荐版（**未前进**） |
| `next` | `0.2.0-rc.2` | rc 线（**未前进**） |
| `alpha` | `0.2.1-alpha.3` | 预览版（本次目标） |

`@deepseek-ai/dsh` 已发布版本尾部序列：

```

```

**结论**：`latest`/`next` 仍停在 `0.2.0-rc.2`，alpha 线继续跑在它们之前。这与 Dockerfile
既有注释的告诫一致 —— **升级只能写全版本号**，用 `@latest` 会拿到更旧的 `0.2.0-rc.2`。
本次是**同一 alpha 线内的小版本前进**（alpha.2 → alpha.3），不涉及稳定性线切换。

### 2.4 三个新增包的行为（读 README + lib 入口确认）

| 包 | 行为摘要 | 模型可见性 |
|---|---|---|
| `dsh-api-remote-access` | 决定**非 owner Peer** 可调用哪些 Remote 方法、可接收哪些转发事件；业务包注册 role/policy，Gateway 在解析参数前先问它。**owner（`{kind:'owner'}`）永远不被检查** | **无**（"registers nothing model-facing"） |
| `dsh-client-ui-secret-mask` | 发送的用户文本中**识别到的凭据**在 Web 上按掩码绘制（保留前 8 字符，其余画 `*`）；**只改绘制**，消息正文、复制动作、模型输入均保持原文 | **无**（纯 Client 显示层） |
| `dsh-harness-dev-context` | 告诉模型 DSH 实现 checkout 位置、GUI 与 "this page" 的关系、以及服务它的 URL。**系统提示只携带无值指引**，具体路径与 URL 作为运行时上下文注入，故换目录/换端口启动**不会重写会话已记录的系统提示** | **有**（模型会得知容器内 checkout 路径与公开 URL） |

**对本项目的评估**：

- `remote-access`：本项目是**单用户容器部署**（默认装 `@xgone/dsh-remote` 做密码+MFA 认证），
  访问者即 owner，**该机制对本项目无行为影响**。它是上游为"多租户 / 非 owner 共享"场景引入的
  安全增强，**不构成能力面扩大**。判定：**跟随上游默认，无需收敛**。
- `ui-secret-mask`：纯显示层，且方向是**降低凭据泄露风险**（截图/投屏场景）。判定：**受益，无需动作**。
- `harness-dev-context`：⚠ **本次唯一"模型可见"的能力面变化**。模型会知道 harness checkout 在
  `/opt/dsh/lib/node_modules/@deepseek-ai/dsh/`（容器内路径）以及 Web GUI 的公开 URL。
  **评估：可接受** ——
  1. 该路径在容器内**本就对 uid 1000 可读**（dsh 自己就跑在那里），模型通过 `tool-bash` /
     `tool-fs` 本来就能发现它，本项只是**省去了发现步骤**；
  2. GUI 公开 URL 是**本项目自己就在向模型公告的信息** —— entrypoint 已通过 `DSH_PUBLIC_URL`
     让 dsh 打印并公告对外地址（见 docs/07 的 3.6 节），本项与之**同向而非新增泄露**；
  3. 它**不改变系统提示**（README 明确"without letting either change the system prompt"），
     故不影响会话的可复现性。
  4. 若确需关闭：在 profile 的 `cordis.patch.yml` 加 `- id: harness-dev-context` +
     `disabled: true` 即可（本项目**当前不做**，仅记录该开关备查）。

### 2.5 plan mode 的结构重构（本次最需要理解的一项）

alpha.3 对 plan mode 做了一次**结构性重构**，不是能力收缩：

| 维度 | alpha.2 | alpha.3 | 语义 |
|---|---|---|---|
| 组 id | `plan-mode` | **`planning`** | 仅改 id，`isolate.planMode: true` 不变 |
| `toolFilter.deny: [schedule_*]` | 6 处 | **0 处（全部移除）** | 与 `RETIRED_BUNDLES` 已退休 `schedule-bundle` 一致 —— 该 bundle 已不在组合内，**无需再屏蔽其工具** |
| 组内 `tool-fs` 声明 | 无 | **有**（`read:false, readImage:true, write:false, edit:false`） | 显式声明 plan mode 下的 fs 权限：**只读图像、禁读文件/写/改** |
| 组内 `compaction` 子组 | 无 | **有**（含 `compaction-basic` + `command-compact`） | 在 plan mode 下也允许上下文压缩与 `/compact` 命令 |
| plan mode section 文本 | "until exit_plan_mode **succeeds** or the user switches" | "until the user **approves your plan** through exit_plan_mode" | 措辞澄清：**评审通过**才算离开 plan mode |

**判定：这是一次"把隐式约束改为显式声明"的重构，方向是收紧而非放开** ——
alpha.2 靠提示词规劝"不要写文件"，alpha.3 直接在组内把 `tool-fs` 的
`read/write/edit` 声明为 `false`。对**本项目零影响**（本项目不使用 plan mode 定制、
不引用 `toolFilter`、不引用 schedule 工具，见 §三）。

> 📌 已知的**非问题**：`toolFilter` 机制本身**并未从 alpha.3 移除** —— 它仍存在于
> `dsh-tool-subagent`、`dsh-permission-presets` 等包中（用于子代理描述符的
> `ToolRestriction`）。消失的只是 **plan mode 对 schedule 工具的那 6 处 deny**。
> 这两件事必须分清，否则会得出"上游删了 toolFilter 机制"的错误结论。

## 四、⚠ 最容易搞错的一点：`DSH_PUBLIC_URL_MIN_VERSION` 不跟着升

本项目有**两个**含 `0.2.1-alpha.*` 字样的地方，语义完全不同：

| 位置 | 语义 | 本次是否应改 |
|---|---|---|
| `Dockerfile` 的 `ARG DSH_VERSION` | **本镜像当前锁定/安装的版本** | ✅ **改** → `0.2.1-alpha.3` |
| `scripts/librescue.sh` 的 `DSH_PUBLIC_URL_MIN_VERSION` 默认值 | **`--public-url` 这个选项"从哪个版本开始存在"**（能力起点） | ❌ **不改**，保持 `0.2.1-alpha.1` |

**为什么不能一起改**：守卫逻辑是 `ver_gt "$_sp_ver" "$_sp_min"` —— 即"卷内版本**不严格大于**
起点"才算支持。若把起点误升到 `alpha.3`，则**卷内 dsh 为 `alpha.1` 或 `alpha.2`** 的用户
（合法状态：用户可以自行覆盖 `DSH_VERSION`、或用旧卷升级上来）会被判"不支持 `--public-url`"，
**静默失去地址公告**。功能无声退化、且无任何告警 —— 正是本项目一贯要避免的那类事故。

同理，`docs/07` 中英表里 `DSH_PUBLIC_URL_MIN_VERSION` 的默认值说明、`.env.example` 第 71 行
"仅 dsh >= 0.2.1-alpha.1 生效"的注释、`docker-compose.yml` 第 95/107 行注释 —— **全部保持不变**；
`scripts/t/test-public-url-guard.sh` 中把 `alpha.1` 当作起点边界的测试用例同理 **不改**。

> 📌 判据（每次升级都适用）：凡是描述"**能力起点** / 兼容下限"的，锚定 `alpha.1`；
> 凡是描述"**当前锁定版本**"的，跟随最新 `ARG DSH_VERSION`。

## 五、端到端实测：认证插件注入链路（本项目真正的耦合点）

本项目的**核心功能耦合**不是某个 dsh API，而是这条链路：

```
镜像 seed /opt/dsh-remote-seed
   └─ scripts/remote-setup.sh 把 @xgone/dsh-remote 复制进 profile 的 node_modules，
      并把包名追加进 profile manifest 的 dsh.profile.bundles
   └─ 插件自带的 cordis.patch.yml 用 `- insert:` 注册 `id: remote` 行
   └─ 本项目在 profile 的 cordis.patch.yml 写 `- id: remote` + config，
      覆盖插件的默认配置（enabled / bootstrap 凭据 / 角色 / 限流 …）
```

**这条链路能否在 alpha.3 下继续工作，是本次升级的真实风险点** —— 因为
dsh 的 patch 机制是"按 row id 定位、后者覆盖前者 config"，一旦上游改了 patch 语义、
或新增了同 id 条目，覆盖就会静默失效或冲突。

### 5.1 实测方法

按项目真实方式构造 profile（两版各一份）：

- manifest：`bundles: ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app", "@xgone/dsh-remote"]`
- 插件本体：从 `/opt/dsh-remote-seed`（版本 `0.3.5`）复制，并按 seed 的 hoisted 布局补齐其依赖
- `cordis.patch.yml`：写项目同款的托管块（`- id: remote` + `enabled: true` + `bootstrap` 凭据）

### 5.2 实测结果

| 验证项 | alpha.2 | alpha.3 | 判定 |
|---|---|---|---|
| `--dump-config` 退出码 | 0 | 0 | ✅ 一致 |
| 插件行是否正确注册（`- id: remote` + `name: '@xgone/dsh-remote'`） | ✅ | ✅ | ✅ 一致 |
| 项目 patch 是否覆盖生效（`bootstrap.username/password` 注入） | ✅ | ✅ | ✅ **两版插件段 diff 为空** |
| 真实 `dsh web` 启动 | ✅ 打印 token | ✅ 打印 token | ✅ 一致 |
| 无凭据 HTTP 探测（宿主进程，配 bootstrap 凭据） | — | **401** | ✅ 认证插件拦截生效 |
| 带 token HTTP 探测（同上） | — | **303** | ✅ 正常放行 |
| 真容器内探测（默认配置，见 §8.2） | **200 / 403** | **200 / 403** | ✅ 一致 |

**结论：认证插件注入链路在 alpha.3 下行为与 alpha.2 完全一致**（插件段 `diff` 为空）。
本项目默认认证能力**不因本次升级发生任何变化**。

> 📌 附带确认：`--dump-config` 渲染中，alpha.3 新增的上游条目是 `remote-access`
