## 一、为什么换线：`--public-url` 已进入 rc 线

### 1.1 背景

本项目此前**长期锁定 alpha 线**，唯一动机是拿到 `--public-url`（修「容器/代理后面 GUI 地址
被说成容器内 `127.0.0.1`」）。Dockerfile 注释与 docs 均记载：「该能力只在 alpha 线可用」。

若该能力已随 `0.2.1` 转正进入 rc 线，则换到 rc 线可**同时拿到该能力与更高稳定性** —— 这正是
本次换线的依据。

### 1.2 决定性证据

| 核查项 | alpha.4 | rc.2 |
|---|---|---|
| `--public-url` chunk 文件名 | `public-url-D_dMK-yI.js` | **`public-url-D_dMK-yI.js`（完全相同）** |
| `parsePublicUrl` 所在 | `dsh-web-app/lib/startup.js` | `dsh-web-app/lib/startup.js` + `lib/index.js` |
| 项目侧守卫判定 | 支持 | **支持**（`rescue_supports_public_url 0.2.1-rc.2` → 真） |
| 真实启动打印 token | ✓ | **✓** |

### 1.3 项目侧守卫本就把 rc 线列为「应支持」

`scripts/t/test-public-url-guard.sh` 的「应支持」用例列表中**早已包含** `0.2.1-rc.1`：

```sh
for v in 0.2.1-alpha.1 0.2.1-alpha.2 0.2.1-alpha.10 0.2.1-rc.1 0.2.1 0.2.2 0.3.0 1.0.0; do
```

这说明项目守卫的设计**从一开始就预期 rc 线支持该能力**，本次换线与该预期一致。

### 1.4 换线方向与稳定性

| 比较 | 结果 |
|---|---|
| `ver_gt 0.2.1-rc.2 0.2.1-alpha.4` | **GT**（前进，非回退） |
| `ver_gt 0.2.1-rc.2 0.2.0-rc.2` | **GT** |
| `ver_gt 0.2.1-rc.2 0.2.1-alpha.1` | **GT** |
| 发布时间 | `rc.2` = 2026-10-17，晚于 `alpha.5` = 2026-10-16 |

**按 semver 数字段**：同数字段下 `rc` 高于 `alpha`，故 `0.2.1-rc.2` > `0.2.1-alpha.4`。
**按稳定性线**：`alpha < rc`，故本次**稳定性提升**。
**发布时序**：rc 线晚于 alpha 线，印证 rc 是从 alpha 转正而来。

### 9.2 未覆盖 / 环境限制

- **本地沙箱**：门禁存在环境性失败，原因是 `/data/dsh` 不可写、缺 `node` —— 已用 `git stash`
  在**未改动代码**上复现同样失败，确证是环境限制而非本次改动引入。真实结论以真机 39/39 为准。
- **`mem_limit` / `cpus` 未应用**：验证机为嵌套 DinD（cgroupv2 threaded 模式），无法施加
  内存/CPU 限额。与历次升级一致。
- **`e2e-rescue-on-host.sh` / `e2e-rescue-diagnose-on-host.sh` 未执行**：脚本头部明确要求
  「宿主机上已有健康 dsh 容器」并会短暂中断 web、可能污染宿主现场，不适于在验证机执行。
  已在真机执行的是自建临时容器的 `e2e-container-selftest.sh`。
- **多架构 arm64 未在真机验证**：真机为 amd64。arm64 由 CI 构建产出，未在真机运行。
- **新增的 web 搜索/抓取 provider 未做功能性调用测试**：本次只验证「它被装载且配置指向既有
  环境变量」，未实际发起一次搜索/抓取请求（那需要真实 API 配额与网络出口）。

### 9.3 结论的可信范围

「能力面仅纯增量」的结论**基于渲染配置对照**（这是 DSH 判定实际装载哪些条目的权威输出）
以及**真实启动 + HTTP 边界实测**。未对全部 300 个变动包做逐行代码审计 —— 那既不必要
（上游整体发版）也不可行。若上游存在仅在高负载/长会话下才显现的行为变化，本次验证**不覆盖**。
