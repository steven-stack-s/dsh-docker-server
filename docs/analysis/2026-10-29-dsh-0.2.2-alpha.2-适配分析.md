> 升级对象：`dsh-docker-server` 的 `ARG DSH_VERSION`，从 `0.2.1-rc.2` → `0.2.2-alpha.2`
> 分析日期：2026-10-29
> **本次性质：跨入新的 0.2.2 数字段（前进），同时从 rc 线回到 alpha 线（稳定性退一步）**
> 对照基线：`0.2.1-rc.2`（隔离安装，306 包） vs `0.2.2-alpha.2`（隔离安装，331 包）

> 但有一项用户可见的行为变化（裸访问 200 → 401）需要告知。**

## 一、版本线现状与"跟随哪个版本"的判定

### 1.1 dist-tag 实测（2026-10-29）

| tag | 指向 | 与上一轮对比 |
|---|---|---|
| `latest` | **`0.2.1-rc.2`** | 从 `0.2.0-rc.2` 前进 —— **正是本项目上一轮锁定的版本** |
| `next` | **`0.2.1-rc.4`** | 从 `0.2.1-rc.2` 前进（0.2.1 数字段内继续） |
| `alpha` | **`0.2.2-alpha.2`** | 从 `0.2.1-alpha.5` 前进，**跨入 0.2.2 新数字段** |

一个值得记录的观察：**本项目上一轮锁的 `0.2.1-rc.2` 已经转正为 `latest`**。这说明本项目跟版本
的节奏是**领先于 stable 推荐版**的 —— 但这也意味着锁 alpha/rc 线必然要承受上游继续前进。

### 1.2 版本序列（实测 `npm view versions`）

```
0.2.1-alpha.5 → 0.2.1-rc.1 → 0.2.1-rc.2 → 0.2.1-rc.3 → 0.2.1-rc.4 → 0.2.2-alpha.2
```

⚠ **`0.2.2-alpha.1` 不存在**：实测 `npm view @deepseek-ai/dsh@0.2.2-alpha.1` 返回 **404**，
`versions` 中 `0.2.2` 只有 `alpha.2`。记录这一点是为了避免后续核对时误以为漏装了一个版本。

### 1.3 发布时序（实测 `npm view time`）

| 版本 | 发布时间（UTC） |
|---|---|
| `0.2.1-rc.2` | 2026-10-17T08:36 |
| `0.2.1-rc.3` | 2026-10-23T07:54 |
| `0.2.1-rc.4` | 2026-10-26T15:28 |
| `0.2.2-alpha.2` | **2026-10-27T19:10** |

### 1.4 判定：跟 `0.2.2-alpha.2`

用户明确要求跟随 `0.2.2-alpha.2`，且它是**当前最新版本**（发布时间最晚、版本号最高）。
但必须如实记录它的代价：

- **数字段前进**：`0.2.2-alpha.2` > `0.2.1-rc.4`（`0.2.2` > `0.2.1`），不是回退。
- **稳定性线退一步**：上一轮我们在 **rc** 线（比 alpha 稳定）；本次回到 **alpha** 线。
  原因是 `0.2.2` 数字段**目前只有 alpha**，还没有 rc。
- **替代方案**：若稳定性优先，可锁 `0.2.1-rc.4`（留在 0.2.1 数字段、保持 rc 线），代价是不跟新数字段。

## 五、⚠ 认证行为变化（本次最需要告知用户的一项）

### 5.1 现象（实测）

| 请求 | `0.2.1-rc.2` | `0.2.2-alpha.2` |
|---|---|---|
| `GET /`（**无** token） | `200` | **`401`** |
| `GET /?token=<tok>` | `200` | **`303`** → 跳 `./` 并下发 cookie |
| `GET /`（带 cookie） | — | **`200`** ✅ |
| `GET /api`（带 cookie） | `403` | **`403`**（未变，远端插件门控） |

401 的正文：

```
dsh web authentication required; reopen the URL printed by dsh web.
```

来源：`dsh-client-connection/lib/index.js` 的 `writeUnauthorized()`。

### 5.2 性质：安全加固，不是故障

cookie 下发属性（实测）：`HttpOnly` + `SameSite`。认证 payload 校验包括
`authority` 绑定、`issuedAt` / `expiresAt` 窗口、`maxAgeMilliseconds` 上限 —— 这是一套
正经的会话认证实现，属于**收紧默认安全性**。

### 5.3 是否阻断容器使用？—— 实测不阻断

这是我最担心的点（本项目刻意在日志里**不打印凭据**，见 `scripts/librescue.sh` 第 149 行
「本提示刻意不含任何凭据」），所以专门做了三组验证：

1. **token 不绑定 Host authority**：用 `Host: 192.168.1.88:3080`（模拟经 socat 从宿主访问）
   携带 token 请求 → **`303` 成功**，随后 cookie 请求 → **`200`**。
   ⇒ 从宿主浏览器访问可用。
2. **设了 `DSH_PUBLIC_URL` 时** dsh 直接打印**对外地址 + token**：
   ```
   dsh web: https://app.example.com/?token=cbdPR7cOJbn6qWQF2m5AwP3pn1tlnNgf8rIJgc2n9ZM
   ```
   ⇒ 可直接点开。
3. **未设 `--public-url` 时** dsh 打印容器内地址 + token（`http://127.0.0.1:3081/?token=...`）：
   ⇒ 用户从 `docker logs` 取 token、换成宿主地址访问即可（即上面第 1 组验证的路径）。

### 5.4 健康检查是否受影响？—— 不受影响（已核对代码）

这是必须确认的第二个关键点，因为 401 有可能让就绪探测误判失败。逐层核对：

| 探测层 | 实现 | 401 是否影响 |
|---|---|---|
| Dockerfile `HEALTHCHECK` | `net.connect(3081, '127.0.0.1')` —— **纯 TCP** | ❌ 不影响 |
| `scripts/probe-ready.js` L1 | `net.connect` TCP | ❌ 不影响 |
| `scripts/probe-ready.js` L2 | `http.request(path:'/')`，回调注释明确写 **「任何状态码都算 HTTP 栈就绪」** | ❌ 不影响 |
| `scripts/probe-ready.js` L4 | 检查正文是否含 4 个启动失败标志 | ❌ 不影响（见下） |

L4 的四个失败标志 vs 401 正文（实测逐项核对）：

| 标志 | 400 正文是否命中 |
|---|---|
| `/Failed to load plugins/i` | ✓ 未命中 |
| `/did not activate/i` | ✓ 未命中 |
| `/dsh-boot-(error\|failed)/i` | ✓ 未命中 |
| `/required startup failure/i` | ✓ 未命中 |

401 正文只有 68 字节：`dsh web authentication required; reopen the URL printed by dsh web.`
⇒ **不会误判为启动失败。**

### 5.5 仍需告知用户的行为差异

虽然是安全加固、且不阻断，但这是**用户可感知的变化**：

- 以前：浏览器输 `http://<host>:3080` 直接进 GUI。
- 现在：需要**先带 token 访问一次**（或带 `DSH_PUBLIC_URL` 让日志直接给出可点链接），
  之后靠 cookie 就不再需要 token。

这一点已写入 `CHANGELOG` 与 `docs/03`。

## 七、差异规模

| 口径 | `alpha.3→alpha.4` | `alpha.4→rc.2` | **`rc.2→0.2.2-alpha.2`** |
|---|---|---|---|
| 全树 diff（排除 `*.map`/`*.d.ts`） | 11,802 | 11,114 | **100,461** |
| 版本号变化的包数 | 289 | 300 | **301**（共同包 305 个中） |
| 渲染配置 diff | 9 行 | 6 行 | **45 行** |
| 包级变化 | +4 / −3 | +2 / −0 | **+26 / −1**（实际装载 +6） |
| 移除包数 | 3 | 0 | **1** |

> **测量方法备注（沿用上一轮的教训）**：全树 diff 在受限环境下耗时**数分钟**，且极易被
> `timeout` 截断而给出偏小的假值（上一轮曾被截断为 5,136 / 8,047，真实值是 11,114）。
> 因此本轮**只在带完成标记（`DIFF-DONE`）时才采信数值，绝不用中途读数**。
> 本轮取得完成标记后读得 **100,461 行**，故采信该值。
>
> ⚠ **这个数字比前两轮大近 10 倍，需要正确解读**：它主要来自**上游整体发版**
> （301 个共同包版本号全部变动）+ **新增 26 个包的文件全量计入**（`diff -r` 会把只在
> 新版本里存在的文件逐行计入），**不代表本项目受影响面变大**。判断影响面仍以
> **实际装载的 6 个包 / 45 行渲染差异 / 逐契约核对**为准 —— 这正是"不要用 diff 行数判断
> 升级风险"的原因。

## 九、验证边界（诚实说明）

### 9.1 已完成的验证

1. 两版隔离安装，包级精确对照（`comm`），逐包归属核查
2. `--public-url` 三重复核（chunk 名 / `parsePublicUrl` / 真实启动打印对外地址）
3. 两版渲染配置全量 diff（45 行，逐条解释）
4. 两版注入认证插件后渲染，插件段逐字节对照（并与 alpha.4 三方对照）
5. 两版真实启动 + HTTP 边界四步探测（裸 / token / cookie / api）
6. token 与 Host authority 解绑验证（模拟 socat 宿主访问）
7. `--public-url` 下 token URL 形态验证
8. 401 正文与 `probe-ready.js` 四个失败标志逐项核对
9. 健康检查实现核对（Dockerfile HEALTHCHECK + probe L1/L2/L4）
10. 真机构建，镜像内 seed / pnpm / 插件版本自证
11. 真机全硬化启动（只读根 FS、cap-drop、no-new-privileges、三卷）
12. 真机全量门禁 + e2e 容器自检

### 9.2 未覆盖 / 环境限制

- **本地沙箱**：`spill-local` 报 `EACCES`（`/data/dsh/tmp` 不可写）—— **在 `rc.2` 下同样出现**，
  已确证是环境限制。真实结论以真机门禁为准。
- **`mem_limit` / `cpus` 未应用**：验证机为嵌套 DinD（cgroupv2 threaded 模式）。
- **`e2e-rescue-on-host.sh` / `e2e-rescue-diagnose-on-host.sh` 未执行**：脚本头部要求
  「宿主机上已有健康 dsh 容器」并会短暂中断 web、可能污染宿主现场。
- **arm64 未在真机验证**：真机为 amd64，arm64 由 CI 构建产出。
- **20 个未装载的新包未做功能评估**：它们不进入本项目 profile，故不影响；但若用户以后
  自行在 profile 里加装这些 bundle（forge / liveshare / cua 等），需单独评估。
- **新版 GUI 前端未做人工交互测试**：本次只验证到 HTTP 层（401/303/200/cookie）与渲染配置。
  UI 层面的变化（新增的 file-drag / message-quotes / deliverable-file-references 等交互）
  **未逐个人工点击验证**。

### 9.3 结论的可信范围

「仅 6 个新增包（7 个渲染条目）实际生效」的结论基于 **bundle patch 精确匹配 + 渲染对照**，这是权威口径。
「认证变化不阻断」基于**真实启动 + 多 Host 组合的 HTTP 实测**。
未对 301 个变动包做逐行代码审计 —— 上游整体发版，这既不必要也不可行。若上游存在仅在高负载/
长会话下才显现的行为变化，本次验证**不覆盖**。

## 十、历次升级对比

| 升级 | 性质 | 包级变化 | 实际装载条目 | 会话格式 | 渲染差异 | 需备份 |
|---|---|---|---|---|---|---|
| 0.1.6 → 0.1.7 | 同线 | +15 / −6 | — | **V3→V4** | 较大 | **是** |
| alpha.3 → alpha.4 | 同线 | +4 / −3 | +3（禁用行） | 4 | 9 行 | 否 |
| alpha.4 → rc.2 | **换线**（alpha→rc） | +2 / −0 | +2 | 4 | 6 行 | 否 |
| **rc.2 → 0.2.2-alpha.2** | **跨数字段 + 回 alpha 线** | **+26 / −1** | **条目 +7 / −6（净 +1）** | 4 | **45 行** | **否** |

**本次特点**：
1. 首次**跨数字段**升级；
2. 首次出现**实际装载条目减少**：`tool-presentation`、`tool-subagent-list-agents`、
   `ui-deepseek-model-label-1017` 三项消失，新增 7 项，**条目净 +1**（299 → 300）；
3. 首次出现**用户可感知的认证行为变化**（裸访问 200 → 401）；
4. 包级变化量最大（+26），但**只有 6 个真正装载（7 个渲染条目）** —— 这正是"看包数会误判"的典型案例。
