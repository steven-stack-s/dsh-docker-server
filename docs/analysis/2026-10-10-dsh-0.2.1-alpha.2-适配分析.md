# DSH 0.2.1-alpha.1 → 0.2.1-alpha.2 适配分析

> 分析日期：2026-10-10
> 对照基线：`@deepseek-ai/dsh@0.2.1-alpha.1`（本镜像 `ARG DSH_VERSION` 当前锁定版）
> 目标版本：`@deepseek-ai/dsh@0.2.1-alpha.2`（npm dist-tag `alpha`）
> 方法：**两版本隔离前缀完整安装 + 全树逐文件 diff + 真实 `--dump-config` / 真实 `dsh web` 启动对照**；npm 元数据仅作版本存在性旁证
> 分析环境：`/workspace/code/.tmp-run/dshinst02/{old,new}`（npm 隔离安装）

---

## 〇、先说结论

| 判定 | 结论 |
|---|---|
| 部署机制是否需要改 | **不需要**。seed → 挂载卷复制 → 启动链路未变；`ver_gt` 实测判定 `0.2.1-alpha.2 > 0.2.1-alpha.1`（GT），卷内升级**不会被 seed 顶回去** |
| 是否有破坏性变更 | **没有会话/设置数据格式换代**。`SESSION_FORMAT_VERSION` 两版**均为 4**，迁移包集合完全相同（`v0..v4` 五个，无新增）—— 与 0.1.6→0.1.7 那次「V3→V4 单向迁移」性质**根本不同**，本次**不需要升级前备份会话** |
| 最大风险 | **base 默认启用的条目变了**：新增 `working-directory` + `tool-working-directory` 两条**默认生效**的 base 条目（后者给模型一个可 `cd` 的工具）。在容器里这是**能力面扩大**，需评估是否要在本项目侧收敛 |
| 会不会起不来 | **不会**。web / lifeboat 两个 profile 均在 alpha.2 下成功组合（`--dump-config` 退出 0）；`RETIRED_BUNDLES` 仍**只含** `schedule-bundle`，本项目零引用 |
| `--public-url` 是否还在 | **在**，且是**同一份** `parsePublicUrl` 模块（chunk 名 `public-url-D_dMK-yI.js` 两版一致）。真实启动实测打印 `dsh web: https://dsh.example.com/?token=...` —— 本镜像锁 alpha 线的唯一动机**继续成立** |
| HMR 加固是否还成立 | **成立**。`dsh-base/cordis.patch.yml` 的 `hmr` 条目两版**逐字节相同**（`disabled: !!js "!ctx.get('profileContext')"` + `config.root: []`）。注：本项目自 2026-09-30 起**已不再干预 HMR**，故此项只是"契约未变"的确认 |
| 需要动手改的地方 | **1 处必改**（`ARG DSH_VERSION`），**5 处连带**（README 徽章 ×2、docs/03 中英 dist-tag 表、CHANGELOG 新增段落——均由门禁强制） |

> ⚠ **`DSH_PUBLIC_URL_MIN_VERSION` 必须保持 `0.2.1-alpha.1` 不变**。它是 `--public-url` 的
> **能力起点**（"该选项从哪个版本开始存在"），**不是**"本镜像当前版本"。跟着升到 alpha.2 是
> 语义错误：会让"卷内 dsh 恰为 alpha.1"的用户被守卫误判为"不支持"而**失去地址公告**。
> 详见 §四。

```yaml

- id: tool-working-directory
  name: '@deepseek-ai/dsh-tool-working-directory'
```

**其他条目变化**（`diff` 实测）：

| 位置 | 变化 | 影响 |
|---|---|---|
| `session-title` 的 `maxOutputTokens` | `64` → `4096`（并补了说明注释） | 仅标题生成的输出上限，**无部署影响** |
| `skill-badge` 条目 | **被移除**（原为 `disabled: true`） | 本项目未引用，无影响 |

本就以 `uid 1000` 运行、可读写 `/data/dsh` 与工作区；该工具只改"当前目录"，不绕过任何
既有 fs 策略（`ctx.fs` 的 workspace 围栏仍在其上游生效）。**判定：可接受，跟随上游默认**，
但记入本文以便日后收紧时有据可查。

## 四、⚠ 最容易搞错的一点：`DSH_PUBLIC_URL_MIN_VERSION` 不跟着升

本项目有**两个**含 `0.2.1-alpha.1` 字样的地方，语义完全不同：

| 位置 | 语义 | 本次是否应改 |
|---|---|---|
| `Dockerfile` 的 `ARG DSH_VERSION` | **本镜像当前锁定/安装的版本** | ✅ **改** → `0.2.1-alpha.2` |
| `scripts/librescue.sh` 的 `DSH_PUBLIC_URL_MIN_VERSION` 默认值 | **`--public-url` 这个选项"从哪个版本开始存在"**（能力起点） | ❌ **不改**，保持 `0.2.1-alpha.1` |

**为什么不能一起改**：守卫逻辑是 `ver_gt "$_sp_ver" "$_sp_min"` —— 即"卷内版本**不严格大于**
起点"才算支持。若把起点误升到 `alpha.2`，则**卷内 dsh 恰为 `alpha.1`** 的用户（合法状态：
用户可以自行覆盖 `DSH_VERSION` 或用旧卷）会被判"不支持 `--public-url`"，**静默失去地址公告**。
功能无声退化、且无任何告警 —— 正是本项目一贯要避免的那类事故。

同理，`docs/07` 中英表里 `DSH_PUBLIC_URL_MIN_VERSION` 的默认值说明、`.env.example` 第 71 行
"仅 dsh >= 0.2.1-alpha.1 生效"的注释、`docker-compose.yml` 第 95/107 行注释 —— **全部保持不变**。

> 📌 判据：凡是描述"**能力起点** / 兼容下限"的，锚定 `alpha.1`；凡是描述"**当前锁定版本**"的，
> 跟随 `alpha.2`。这条区分在下次升级时同样适用。

### ⚠ 真机观察到一个**既有**首启现象（与 alpha.2 无关）

首次启动时 entrypoint 会以 root 写出 `/data/dsh/profiles/web/cordis.patch.yml`（mode `0600`），
随后降权到 uid 1000 的 dsh **读不了它**，于是：

```
Error: dsh: failed to read overlay /data/dsh/profiles/web/cordis.patch.yml:
       EACCES: permission denied
```

自愈 4 次耗尽后置 lifeboat 标记 → 容器按 `restart: unless-stopped` 自动重启 →
**第二次启动进的是 lifeboat profile**（`Up (healthy)`，但非 web）→ 需要**手动 `docker restart dsh`
一次**才回到 web profile（实测：restart 后 `boot attempt 1/4 (profile=web)` → healthy → HTTP 可达）。

**归属判定：这是 entrypoint 的既有顺序问题，不是 alpha.2 引入的。** 证据：

- 两版 `dsh-app-boot` 的 `loadOverlayPatches` **代码路径完全相同** —— 均为
  `readFileSync(file,"utf8")` 失败即 `throw new Error("failed to read overlay …")`
  （alpha.1 在 `index.js:3633`，alpha.2 在 `:3685`，行为一致）；
- 写该文件的是本项目自己的 `scripts/remote-setup.sh`，读它的是 entrypoint 的降权后进程 ——
  **整条链路都是本项目脚本**，不随 dsh 版本变化；
- entrypoint 注释本身已预言该失败模式（"root 属主的插件树让 uid 1000 读不到 → profile 加载
  失败 → 自愈耗尽 → 进 lifeboat"），并说明设计上由"**下一轮**的 ③ 属主对齐收尾"——
  即首启失败一次在作者预期内，但"第二次即进 web"并未发生（第二次被 lifeboat 标记接管）。

> 📌 该现象**不影响本次版本跟随的正确性**，但**与 `docs/zh-CN/01-快速开始.md` 中"首次启动
> 秒级就绪"的表述有出入**。它属于**独立的既有缺陷**，建议单独排期修复（例如：⑤b 写完
> `cordis.patch.yml` 后立即 `chown` 给运行用户，或把该文件改由运行用户创建），
> **不在本次改动范围内**。

## 八、诚实边界

- 本文"无影响"的**静态结论**基于包级 diff + 真实 CLI 启动；**真机构建与运行已验证**（见
  §六之二），但验证机为嵌套 DinD，其 **`mem_limit` / `cpus` 无法应用**（cgroupv2 threaded

  `pids_limit` / `read_only` / `tmpfs` / `cap_drop` / `security-opt` 均正常）。
